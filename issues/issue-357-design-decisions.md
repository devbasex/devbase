# #357: 決定の記録

[issue-357-design.md](issue-357-design.md)（#357 の設計）の決定と、その根拠にした実測を持つ。
不変条件（I1〜I9）と受け入れ条件の番号は、設計と要求（[issue-357-requirements.md](issue-357-requirements.md)）のものを指す。

## 決定の記録

### 決定 1: リンクの段のロックと張り替えの試行の両方を入れる

ロックだけでは、修正前の手順で張る相手（ロックを取らない）と重なったときに落ちるため、受け入れ条件 7 を
満たせない。張り替えの試行だけでは、共有のリンクは正しくなるが、退避とプレースホルダが重なる経路が残り、
対象範囲の「リンクの段の全体を同時に走らせた結果が、1 つずつ順に走らせた結果と同じ」を、処理ごとの場合分けで
示すことになる。両方を入れると、修正後どうしは順に走るため結果が同じになり、ロックが効かない相手と場面は
張り替えの試行が受ける。ロックを取れないときの退避とプレースホルダは、排他の作成が受ける（決定 10）。

根拠: Mission / Vision（MVV 版 1）

### 決定 2: ロックは共通のボリュームのルートのディレクトリそのものに掛け、ロックのためのファイルを作らない

退避は共通のボリュームへ書き、共通のボリュームはすべてのコンテナが共有する。ここに 1 つだけロックを置けば、
グループのボリュームの処理も含めてリンクの段の全体が順に走る。ディレクトリそのものに掛けるため、ボリュームに
残るものが無く、修正前の手順とスナップショットから見える並びが変わらない（I8）。グループのボリュームに
ロックのファイルを置く方式は、退避の重なりを防げず、ボリュームにファイルが残るため採らなかった。別の
グループのコンテナも順番を待つが、リンクの段 1 回は base イメージのコンテナの中で 0.1 秒ほどである。

根拠: Vision（MVV 版 1）

### 決定 3: ロックは 10 秒まで待ち、取れなければ警告を出してロックなしで進む

持ち主が kill されたときはカーネルがすぐにロックを外すが、止まったまま終わらない持ち主がいると、上限なしでは
ホストのすべてのコンテナの起動がそこで止まる。ロックなしで進んでも、共有のリンクは張り替えの試行で正しく
なり、退避とプレースホルダは排他の作成で 1 つのプロセスだけが書く（決定 10）。失うのは、リンクの段の全体が
1 つずつ順に走る保証だけである。待ち切れないときに非 0 で終わる方式は、1 つのコンテナの不調をほかのコンテナの起動の失敗へ広げるため採らなかった。10 秒は、8 個が順に
走る所要（実測で 0.75〜1.9 秒）より長く、非機能の条件の 30 秒より短い値として置く。

根拠: Mission（MVV 版 1）

### 決定 4: 張り替えは「消す → `ln -sn` → 読み直す」の繰り返しにし、一時的な名前と置き換え（rename）を使わない

一時的な名前で張ってから `mv -T` で置き換える方式は、位置が実体のディレクトリのときに置き換えられず、結局
消す手順が要る。`mv -T` は macOS の `mv` に無く、既存の 35 件が開発者の端末で走らなくなる。途中で kill されると
一時的な名前がボリュームに残る。読み直しで判定する方式は、base イメージと macOS の両方にあるコマンドだけで
書け、ボリュームに余分な名前を作らない（I8）。置き換えの利点である「リンクが無い瞬間が無い」は、修正後
どうしではロックが与え、修正前の手順の相手に対しては相手の側が消すため、どちらの方式でも得られない。

根拠: P1（MVV 版 1）

### 決定 5: ロックはサブシェルの中だけで持つ

リンクの段の関数は、サブシェルを開き、そのサブシェルにだけ付けた fd で共通のボリュームのルートを開いて
ロックを掛け、同じサブシェルの中で本体を呼ぶ。サブシェルを抜ければ、成功でも失敗でも fd が閉じる。
呼び出したシェルで fd を開く方式は、閉じ忘れると entrypoint が最後に `exec` するコマンドへ fd が引き継がれ、
コンテナが動いている間ロックを持ち続けるため採らなかった（I7）。

根拠: Mission（MVV 版 1）

### 決定 6: 張る操作に `-n` を付ける

修正前の手順の `ln -s` は、位置が既にディレクトリを指すリンクになっていると、失敗せずに、その先のディレクトリの
中へリンクを作って 0 で終わる。同時起動で相手が先に張ったときにこの形になり、共通のボリュームの `plugins` の
中に `plugins` という入れ子のリンクが残る（下の実測）。`-n` を付けると、位置そのものを対象にして失敗し、
読み直しへ進む。

根拠: Value 2（MVV 版 1）

### 決定 7: `flock` が無い環境ではロックなしで進み、同時実行のテストを skip しない

base イメージには `flock` が必ずあるが、開発者の macOS には無い。無いときに止めると、既存の 35 件が macOS で
走らなくなる。ロックなしでも、張り替えの試行と排他の作成（決定 10）で受け入れ条件 1〜7 を満たすため
（下の実測）、同時実行のテストは macOS でも走らせる。理由を示して skip するのは、ロックそのものを確かめるテスト（I5・I7 と、非機能の
可用性）と、書き込めない状態を作れない root での受け入れ条件 9、Docker かイメージが無いときの受け入れ条件 13
だけである。要求の未決「macOS で走れないテストが出た場合に skip でよいか」は、この範囲の skip として決める。

根拠: 根拠なし（MVV 版 1）

### 決定 8: 張り替えの試行は、ホームのリンクも共有のリンクも同じ関数で行う

同時起動で重なるのは共有のリンクだけだが、リンクを張る関数を 2 つに分けると、位置に実体があるときの扱い
（要求の前提 3）を 2 か所で保つことになる。ホームのリンクでは試行が 1 回で終わり、振る舞いは今と変わらない。

根拠: 根拠なし（MVV 版 1）

### 決定 9: 実物のコンテナでの確認は、イメージを建て直さず、作業ツリーの `entrypoint.sh` をマウントして行う

受け入れ条件 13 は、今ある base イメージ（`devbase-base:latest`）のコンテナに、作業ツリーの `entrypoint.sh` を
読み取り専用でマウントし、使い捨ての名前のボリューム 2 つで 8 個を同時に起動して確かめる。利用者の端末の
イメージのタグを置き換えず、利用者のボリュームにも `devbase up` にも触れない。pytest のテストとして置き、
Docker かイメージが無いときは、base イメージを使う既存のテストと同じ決まりで skip する（CI では skip になり、
完了判定のときに開発者の端末で走る）。イメージを建て直して確かめる方式は、確認のたびに利用者の手元の
イメージが入れ替わるため採らなかった。

根拠: Value 3 / P3（MVV 版 1）

### 決定 10: 退避とプレースホルダは、排他の作成で作れた 1 つのプロセスだけが書く

ロックなしで進むリンクの段（待ち時間の上限を超えた・`flock` が無い）は、退避を同時に始める。今の退避は
「コピー先が無ければ、ディレクトリを作って子を `cp -a` でコピーする」で、2 つが重なると、後から来た `cp -a` が
既にある子のディレクトリの中へ重ねてコピーし（`plugins/<名前>/<名前>`）、`cp` が `File exists` で失敗して
起動が止まる回もある（下の実測）。張り替えの試行だけでは、この経路が残る。対象範囲の「リンクの段の全体を
同時に走らせた結果が、1 つずつ順に走らせた結果と同じ」をロックを取れないときにも満たすため、エントリを作る
操作そのものを排他にし、作れたプロセスだけが中身を書く（I9）。

通常のファイルは bash の noclobber（`set -C` の `>`）で作り、ディレクトリは `perl` から `mkdir(2)` を呼んで作る。
base イメージの `mkdir`（uutils coreutils 0.8.0）は、同時に呼ぶと 2 個以上が 0 で終わるため、作れたプロセスを
1 つに決められない（下の実測）。`perl` は base イメージに今入っており（Essential のパッケージ perl-base）、
道具を足さない（前提 5）。`perl` が無い環境では `mkdir` で作り、止めない（決定 7 と同じ考え）。

採らなかった方式は次のとおりである。

- 一時的な名前へコピーしてから置き換える: kill で一時的な名前がボリュームに残る（I8・決定 4）
- ロックのためのファイルをエントリの隣に置く: kill で残ると、次の起動から退避が行われなくなる（I8）
- ロックを取れないときは非 0 で終わる: 1 つのコンテナの不調を、ほかのコンテナの起動の失敗へ広げる（決定 3）
- ロックを取れないときは退避を飛ばす: 続くリンクの張り替えがホームの `~/.claude` を消すため、イメージの設定を失う
- `gnumkdir`（GNU coreutils の `mkdir`）を呼ぶ: base イメージでは排他だが、CI の runner と macOS に無い名前で、
  環境ごとの分岐が要る
- `python3` から `mkdir(2)` を呼ぶ: base イメージでは排他だが、python3 は Essential のパッケージではない

根拠: Value 2 / Vision（MVV 版 1）

### 決定の根拠にした実測

base イメージの `ln`（uutils coreutils 0.8.0）は、次のとおり振る舞う。

```text
$ mkdir -p /tmp/t/real; ln -s /tmp/t/real /tmp/t/link
$ ln -s /tmp/t/real /tmp/t/link; echo "rc=$?"; ls /tmp/t/real
rc=0
real
$ ln -sn /tmp/t/real /tmp/t/link; echo "rc=$?"
ln: Already exists
rc=1
```

決定 10 のための実測は、2026-10-02 に、同じ 2 つの環境で行った。始めの状態は、空の 2 つのボリュームと、
どのホームにも同じ中身の `~/.claude`（`plugins` の下に子のディレクトリ 12 個・`skills`・`commands`・`CLAUDE.md`・
`settings.json`）である。ロックは入れずに 8 個を同時に始め、終わった後の 2 つのボリュームの並び・リンクの先・
ファイルの中身を、1 個だけ走らせた後と比べた。「張り替えの試行」と「排他の作成」は、設計のとおりに書いた
関数を今の `entrypoint.sh` へ読み込ませたものである。
