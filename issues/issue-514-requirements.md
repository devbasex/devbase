> devbaseにリポジトリ/プラグイン/projectの新規追加コマンドを作りましょう
> * いずれもgithub urlまたはowner/repos 名を引数とする

## 目的

新しいリポジトリを devbase で開発を始められる状態にするまでの手作業（レジストリのファイルの追記・`project.yml` などの配置・PR・マージ・`plugin update`）を、1 回のコマンドか TUI の操作で済ませる。今は [プラグイン開発クイックスタート](docs/plugin-dev/quickstart.md) の手順を人が打つ必要があり、入れ先のプラグインの判断も人の頭の中にある。

## 前提

- 前提 1: 対象は GitHub（github.com）だけである。GitHub 以外の URL は受け付けない
- 前提 2: `gh` がホストに入っていて認証済みである。`gh` は devbase の必須の依存には足さず、この 3 つのコマンドだけが要る
- 前提 3: 利用者はこのコマンドを打つことで、レジストリの既定ブランチへのマージを意図している

## 対象範囲

含む:

- `devbase plugin repo new`・`devbase plugin new`・`devbase project new` の追加
- PR の作成・マージ・手元への取り込み・`plugins.yml` への登録
- `devbase list` の TUI からの同じ 3 つの操作と、プラグインのメニューの組み直し
- シェル補完・CLI リファレンス・`CHANGELOG.md`

含まない:

- 追加したプロジェクトの起動（`devbase up` は打たない。P3）
- `env` の値の登録、`pre-up` などのフック、`Dockerfile` の雛形の出し分け
- 既存のプラグインの `description` にプロジェクト名を書き足す更新
- GitHub 以外のホスト、Organization の作成、`gh` の導入やログインの代行

## 用語

| 用語 | 意味 |
| --- | --- |
| プラグインリポジトリ | 直下に `registry.yml` を持ち、1 つ以上のプラグインを収めた Git リポジトリ。`devbase plugin repo add` で登録するもの |
| 作成フロー | リポジトリ・プラグイン・プロジェクトを足す一連の操作。権限の確認からマージ、手元への取り込み、登録までを含む |

## 受け入れ条件

### リポジトリ（`devbase plugin repo new <URL|owner/repo>`）

- [ ] 1. 前提: 指定のリポジトリが無く、owner に作成できる。操作: 実行する。結果: private のリポジトリができ、`registry.yml` を持つ最初のコミットが既定ブランチに入り、`repos/` に clone され、`plugins.yml` に登録され、終了コードは 0。`--public` のときだけ公開になる
- [ ] 2. 前提: リポジトリがあり push でき、`registry.yml` が無い。結果: `registry.yml` を足す PR が作られてマージされ、手元へ取り込まれて登録され、終了コードは 0
- [ ] 3. 前提: リポジトリがあり push でき、`registry.yml` がある。結果: PR を作らずに登録し、終了コードは 0。登録済みなら変更せず、その旨を出して終了コードは 0
- [ ] 4. 前提: リポジトリがあるが push できない、または無くて owner に作成できない。結果: GitHub にも手元にも何も作らず、理由を出して終了コードは 1
- [ ] 5. `https://github.com/owner/repo`・`https://github.com/owner/repo.git`・`git@github.com:owner/repo.git`・`owner/repo` が同じ結果になり、GitHub 以外の URL は終了コード 1 になる

### プラグイン（`devbase plugin new <URL|owner/repo> [--name <名前>]`）

- [ ] 6. 前提: 登録済みのプラグインリポジトリ。結果: `<名前>/plugin.yml`・`<名前>/projects/`・`registry.yml` の項目を足す PR が作られてマージされ、手元へ取り込まれてプラグインが導入された状態（`devbase plugin list` に出る）になり、終了コードは 0
- [ ] 7. 前提: リポジトリが未登録。結果: 受け入れ条件 1〜4 の分岐を通してからプラグインを足す。分岐が終了なら何も作らない
- [ ] 8. 同じ名前のプラグインが既にあるとき、何も変えずに終了コード 1 になる。名前は「名前の形」に合わなければ終了コード 1 になる

### プロジェクト（`devbase project new <URL|owner/repo> [--plugin <名前>] [--group <名前>] [--name <名前>]`）

- [ ] 9. 前提: 対象のリポジトリを読め、入れ先のプラグインへ push できる。結果: 入れ先の `projects/<名前>/` に `project.yml`・`compose.yml`・`env` を足す PR が作られてマージされ、手元へ取り込まれ、`devbase list` にプロジェクトが出て、終了コードは 0
- [ ] 10. 入れ先の決定: `--plugin` があればそれを使う。無ければ、導入済みで push できるプラグインを候補にし、候補のうち対象と同じ owner のものがあればそれに絞る。1 件なら確認の計画に示して使い、複数で TTY があれば選ばせ、複数で TTY が無ければ候補を出して終了コード 1 になる。候補が 0 件なら終了コード 1 になる
- [ ] 11. グループの決定: `--group` があればそれを使う。無ければ入れ先の既存プロジェクトの最多の値を使う。決まらないとき、TTY があれば聞き、無ければ終了コード 1 になる
- [ ] 12. 対象のリポジトリを読めないとき、同じ名前のプロジェクトが `projects/` か入れ先に既にあるとき、何も変えずに終了コード 1 になる
- [ ] 13. どの経路でも `devbase up` を実行しない

### 3 つに共通

- [ ] 14. `gh` が無い・未認証のとき、何も変えずに次の操作を出して終了コード 1 になる
- [ ] 15. 変更の前に計画（作るもの・マージ先）を示す。TTY があれば確認を取り、断れば何も変えない。TTY が無いときは `--yes` が無ければ何も変えずに終了コード 1 になる
- [ ] 16. 手元の clone に未コミットの変更があっても、その変更は失われず、作業は clone の作業ツリーを汚さない。取り込みが早送りで済まないときは変更を残したまま原因を出して終了コード 1 になる
- [ ] 17. マージできないとき（必須のレビューや検査が足りないなど）、PR の URL と続けるコマンドを出して終了コード 1 になり、`plugins.yml` は変わらない。作業用のブランチと作業場所は成功のときに残らない

### TUI

- [ ] 18. `devbase list` のプラグインのメニューから 3 つの操作を実行でき、引数は CLI と同じ値に解決される。入れ先の選択は TTY の選択肢として出る
- [ ] 19. プラグインのメニューは第 1 階層が用途で分かれ、既存の全操作（一覧・導入・削除・更新・詳細・再同期・移行・リポジトリの一覧/登録/削除/更新）へ届く
- [ ] 20. Esc・←・Ctrl-C のふるまいが既存のメニューと同じである

### 退行しないこと

- [ ] 21. 既存の `plugin` のサブコマンドの引数と出力は変わらない
- [ ] 22. `devbase project new owner/repo` の引数がプロジェクト名として解決されない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 途中で止まったとき、どこまで進んだかと次のコマンドが出力に出る |
| セキュリティ | トークンを引数やログへ出さない。認証は `gh` と `git` の既存の設定に任せる。公開は `--public` のときだけ |
| システム環境 | Linux・macOS で動く。`gh` の最低版は設計で決める |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。サブコマンドの追加のみで、既存のコマンドは互換 |
| データ | `plugins.yml` の形は変わらない |
| 既存の振る舞い | TUI のプラグインのメニューの並びと階層が変わる |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `env -u DEVBASE_ROOT uv run --locked pytest tests/ -q`。`gh` と `git` の push・マージは偽の `gh` と手元の bare リポジトリで置き換える |
| 静的解析・型検査 | `uvx ruff check --select=E9,F63,F7,F82 lib`、`python3 .github/scripts/proper_term_check.py` |
| 手動確認 | 利用者が作業用の Organization かアカウントで 3 つのコマンドを打ち、GitHub の PR とマージ、`devbase list` の表示を見る。TUI の見た目もこのときに見る |
