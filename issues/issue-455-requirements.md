## 目的

- zsh の補完（`etc/_devbase`）を書き換えたとき、候補が出なくなる退行を、利用者の端末に届く前に検査で落とせるようにする
- 今は「分岐の本体に決まった文字列があるか」しか見ておらず、#449 の退行（`devbase up <TAB>` がプロジェクト名を出さない）は一致テストをすべて通った

## 前提

- 前提 1: 既存の静的な検査（`tests/cli/test_name_context_consistency.py` の zsh の比べ方、`tests/cli/test_completion.py` の zsh の内容の検査）は消さずに残す。zsh を起動できない環境で、それが唯一の zsh の検査になるため
- 前提 2: zsh を起動して候補を取る方法は、`zsh/zpty` で対話の zsh を起こし `compadd` を包んで候補を書き出す形が macOS の zsh 5.9 で動くことを #450 のリリース後テストで確かめてある。Linux の zsh で同じ形が動くかはまだ確かめておらず、設計で確かめる
- 前提 3: テストが読む zsh の設定は `zsh -f` と同じく利用者の rc を読まない形とする。利用者の rc（oh-my-zsh などの zstyle・補完の表示）を通した確認は、引き続きリリース後テストで利用者の端末で行う
- 前提 4: テストのプロジェクト名は一時の `DEVBASE_ROOT`（`projects/proj-a`・`projects/proj-b` のような中立の名前だけを持つ）から出す。実の `DEVBASE_ROOT` と `projects/*` に触れない
- 前提 5: 確かめる道は、#450 のリリース後テストで確かめた道を基にした代表の道とする（下の受け入れ条件 2〜5）。`--context` の集合や `[name]` の集合のすべての道を zsh で起動して回すかは設計で決める（回すと時間がかかるため）
- 前提 6: テストだけの変更であり、利用者に見える振る舞いは変えない。`CHANGELOG.md` は書かない（`AGENTS.md` の「Pull Request」）

## 対象範囲

含む:
- zsh を起動して `etc/_devbase` を補完として読み込み、打った行に対して実際に出る候補を集めて比べる pytest のテスト
- zsh が無い・`zsh/zpty` を読めない環境での扱い（受け入れ条件 7）
- CI でこのテストを走らせるための手当て（ランナーへ zsh を入れるなど。設計で走らせると決めた場合だけ）
- 確定仕様 `docs/specifications/cli-argument-resolution.md` の、zsh を起動する検査が無いことを前提にした記述（決定 9・決定 13・検証の節の「手元の zsh で確かめる」の行）の改め

含まない:
- `etc/_devbase`・`etc/devbase-completion.bash` の振る舞いの変更（テストが退行を見つけた場合は別の課題にする）
- bash の補完のテスト（既に bash を実行して `COMPREPLY` を読む形で確かめている）
- 利用者の rc・プラグイン管理・zstyle を通した見た目の確認
- 一致テストが補完の `--context` の余分を比べないこと（#453）、`env` の補完の一覧に `token` と `backend` が無いこと（#454）

## 受け入れ条件

- [ ] 受け入れ条件 1: zsh を起動して `etc/_devbase` を補完として読み込み、打った行に対して補完が出した候補（`compadd` に渡った語）を集めて期待と比べるテストが `tests/` にある。ファイルの内容を読むだけの検査ではない
- [ ] 受け入れ条件 2: 一時の root に `proj-a`・`proj-b` を置いたとき、`devbase up `・`devbase project up ` の後で補完を求めると、候補に `proj-a` と `proj-b` が出ることをテストが確かめる。`devbase login ` では `1` と `2` が出ることを確かめる
- [ ] 受け入れ条件 3: `devbase up -`・`devbase env exec -`・`devbase ct profile up -`・`devbase project post-start -` の後で補完を求めると、候補に `--context` が出ることをテストが確かめる
- [ ] 受け入れ条件 4: `devbase up proj-a -` の後で補完を求めると、候補に `--context` が出ることをテストが確かめる
- [ ] 受け入れ条件 5: `devbase up --context `・`devbase env exec --context ` の後で補完を求めると、候補が 0 件であることをテストが確かめる
- [ ] 受け入れ条件 6: テストが落ちたとき、出力に「打った行・期待した候補・実際の候補」が並ぶ。`etc/_devbase` を `54ed5bf^`（#450 の修正前）の内容に差し替えて流すと、受け入れ条件 2 のテストが落ち、`devbase up ` の実際の候補が `--context` だけであることが出力に出る
- [ ] 受け入れ条件 7: zsh が無い環境、または `zsh/zpty` を読み込めない環境では、テストは他のテストを止めずに終わり、何が欠けていたか（zsh が無い／`zsh/zpty` が無い）を pytest の出力に残す。この環境で飛ばすか落とすかは未決 1 の決定に従う
- [ ] 受け入れ条件 8: 補完が応答しないとき、テストは決めた時間（1 回の補完の要求につき 10 秒）で打ち切って失敗し、テストが終わった後に起動した zsh のプロセスが残らない
- [ ] 受け入れ条件 9: 確定仕様 `docs/specifications/cli-argument-resolution.md` から、「zsh を起動するテストが無い」ことを前提にした記述（決定 9 の「zsh を起動する形は採らない」、決定 13 の「zsh を起動する検査が無く」、検証の節の「手元の zsh で確かめる」の行）が無くなり、新しいテストが何を確かめ、どの環境で走るかが書かれている
- [ ] 受け入れ条件 10: 退行しない: 既存の `tests/cli/test_name_context_consistency.py`・`tests/cli/test_completion.py` の検査が残り、`env -u DEVBASE_ROOT uv run --locked pytest tests/ -q` が手元（macOS）と CI（Linux の Python 3.10・3.13）の両方で通る
- [ ] 受け入れ条件 11: 退行しない: テストは利用者の rc（`~/.zshrc` など）と実の `DEVBASE_ROOT`・`projects/*` を読まず、書かない
