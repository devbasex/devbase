### #224 の本文（`devbase scale` で増やしたインスタンスに `_report_missing_repos` / `_apply_window_titles` が行われない）

> ## 何を見つけたか
>
> `devbase scale` で増やしたインスタンスに、`devbase up` が行う後処理のうち 2 つが行われない。
>
> | 後処理 | `cmd_up` | `cmd_scale` |
> | --- | --- | --- |
> | `_report_missing_repos`（clone できなかった repo を伝える） | 行う | **行わない** |
> | `_apply_window_titles`（VS Code のウィンドウタイトルをコンテナ名始まりに固定する） | 行う | **行わない** |
> | `_push_bao_token` | 行う | 行う（`start=current_scale + 1`） |
> | `./deploy` | 行う | 行う（`current_scale + 1 .. new_scale`） |
>
> そのため、`devbase scale 3` で増やした `dev-2` / `dev-3` は、
>
> - repo の clone に失敗していても何も伝わらない（`devbase up` なら警告が出る）
> - VS Code のウィンドウタイトルが `dev-1` と同じ流儀に揃わない
>
> **実害の観測はまだ無い。** `cmd_up` と `cmd_scale` の後処理の集合が違うことまでが分かっている。
>
> ## どこで見つけたか
>
> #192（`cmd_scale` の長いメソッドと compose config 読み取りの重複）の設計の過程で、
> `cmd_up` と `cmd_scale` の段階の対応表を作ったときに見つけた。
>
> **所在（`main` = `cc71c3c`、v4.0.0 の後）。** PLAN65 / #192 で `cmd_scale` は段階へ分かれているが、
> **後処理の差は残っている。**
>
> ```
> $ grep -n "_report_missing_repos\|_apply_window_titles" lib/devbase/commands/container.py
> 1338:        _report_missing_repos(...)      ← cmd_up だけ
> 1353:        _apply_window_titles(...)       ← cmd_up だけ
> ```
>
> `cmd_scale` の後処理は `lib/devbase/commands/container.py:1695-1702` にあり、
> `_push_bao_token`（`:1695`、`start=current_scale + 1`）と `./deploy`（`:1699-1702`）の 2 つだけである。
>
> `_apply_window_titles`（`:960`）と `_report_missing_repos`（`:1120`）は `scale` だけを受け、
> 開始の番号を受けない。そのまま `cmd_scale` から呼ぶと、既存のインスタンスにも走る。
>
> ## なぜこの変更の範囲外なのか
>
> #192 の受け入れ条件（現在の所在は `issues/old/PLAN65_scale-compose-path.md`）は次の 3 つに限っていた。
>
> - `devbase scale` の Compose 呼び出しを共通経路へ寄せること（子プロセスの環境と起動の対象）
> - `cmd_scale` の段階を関数へ抽出すること（振る舞いを変えない）
> - `docker compose config --format json` の読み取りを 1 つにすること
>
> 後処理を足すのは **`devbase scale` の振る舞いを増やす**変更で、「振る舞いを変えない」抽出の
> 条件に反する。#192 の対象範囲の「含まない」にも
> 「`cmd_scale` の前提の検査そのものの見直し」と並ぶものとして外していた。
>
> **#192 は v3.7.0 で閉じているため、この制約はもう無い。** `cmd_scale` が段階へ分かれた
> いまは、`cmd_up` の後処理の段階に対応する位置へ 2 つを足せばよい。2 つの関数には
> 対象のインスタンスを受ける引数を足し、増やしたインスタンス（`current_scale + 1` から `new_scale`）だけに行う。
> `cmd_up` と `cmd_scale` の後処理を、対象のインスタンスの集合を受ける 1 つの段にまとめる形が合う。
> 開始の番号ではなく集合を受ければ、#371（起動に成功したコンテナだけに後処理を行う）も同じ段で賄える。
> **実環境での `devbase scale` の確認は #246 で行う**ため、そこで後処理の有無も併せて見られる。
>
> ## 直さないと何が起きるか

>   出会う。`devbase up` をやり直すと警告が出るため、そこで初めて分かる

>

### #371 の本文（`up` でコンテナが 1 台でも落ちると、起きているコンテナにも起動の後の処理が行われない）

> ## 何を見つけたか
>
> `devbase project up` は、コンテナの起動を待った後に「起動の後の処理」を順に行う（`lib/devbase/commands/container.py` の `cmd_up`、1333 行付近からの `try`）。
>
> | 処理 | 関数 |
> | --- | --- |
> | clone できなかったリポジトリの報告 | `_report_missing_repos` |
> | プロジェクトの `deploy` スクリプト | `_run_deploy_script_for_instances` |
> | OpenBao の token の配布 | `_push_bao_token` |
> | VS Code の `window.title` をコンテナ名始まりにする | `_apply_window_titles` |
> | エディタの自動オープン | `_maybe_open_editor` |
>
> 起動の待ちで 1 台でも落ちると、`_run_deploy_pipeline` が `DevbaseError`（`Container startup failed: Container dev-2 exited unexpectedly.`）を投げ、**起きている他のコンテナも含めて、これらの処理がすべて飛ばされる**。落ちたコンテナを `docker start` で起こし直しても、これらの処理はやり直されない。
>
> - 再現（2026-09-30）: scale 2 のプロジェクトを新しく足して `devbase project up` した。#357 の競合で `myapp-dev-2` が `ln: Already exists` で落ち、`Deploy failed` で終わった。`myapp-dev-2` を `docker start` で起こすと 2 台とも動いたが、どちらのコンテナの `~/.vscode-server/data/Machine/settings.json` にも `window.title` が無く、VS Code の窓のタイトルがコンテナ名始まりにならなかった
> - 手で `window_title.apply_to_container` を 2 台へ走らせると書けた（処理そのものは動く）
>
> `devbase scale` も同じ形をしている。`cmd_scale` の `_run_scale_pipeline` も `wait_for_containers_ready` を呼ぶため、足した 1 台が落ちると `DevbaseError` で抜け、`_push_bao_token` と `./deploy`（`container.py` の 1695 行付近から）が飛ぶ。
>
> ## なぜ困るか
>
> - 利用者から見ると、コンテナは動いているのに、タイトル・token・エディタの自動オープンが黙って欠ける。原因が `up` の途中の失敗だと気づきにくい
> - token の配布（`_push_bao_token`）が飛ぶと、起きているコンテナで機密を読めない
>
> ## 直し方の見込み（決めること）
>
> - 起動の待ちで落ちたコンテナがあっても、**起きているコンテナには**起動の後の処理を行い、そのうえで失敗として終える。`wait_for_containers_ready`（`lib/devbase/utils/docker.py`）は 1 台が落ちると、他のコンテナが ready になるのを待たずに止まる。起きているコンテナへ後処理を行うなら、待ちの側が「落ちた番号」と「ready になった番号」を分けて返す必要がある
> - 落ちたコンテナの名前と、起こし直す方法（もう一度 `devbase project up` を打つ。`docker start` では起動の後の処理が走らない）を出す
> - または、起動の後の処理だけをやり直す手段（コマンドか、`up` が既に起きているコンテナでも処理をやり直すこと）を用意する
>
> ## 関連
>
> - #357（同じグループのコンテナを同時に起動すると 1 つが落ちる）。#357 が直っても、別の理由で 1 台が落ちたときに同じことが起きる
> - #224（`devbase scale` で増やしたインスタンスに `_report_missing_repos` / `_apply_window_titles` が行われない）。直す場所がこの課題と同じである。起動の後の処理を `cmd_up` と `cmd_scale` で共有し、対象のコンテナの集合を受ける段にする。この課題は起動に成功したコンテナを、#224 は増やしたインスタンスを、その段へ渡す。段の引数の形を 2 度変えないよう、合わせて着手する
>

## 目的

- `devbase up` で起動したインスタンスにも、`devbase scale` で増やしたインスタンスにも、起動できたものには同じ起動の後の処理が届く（#224）
- 1 台が起動できなかったときに、起動できたインスタンスの窓のタイトル・token・エディタが黙って欠けたままにならない。何が欠けたかと、その補い方が `up` / `scale` の出力から分かる（#371）
- 起動の後の処理が誰を対象にするかを、`up` と `scale` が同じ 1 つの決まりで決める。2 つのコマンドの処理の集合が再びずれない

## 現状（2026-10-02 に調べたこと。`main` = `cc71c3c`）

原文の指摘を、コードと既存のテストの読み取りで確かめた。実物の docker では確かめていない。

| 調べたこと | 結果 |
| --- | --- |
| 起動の後の処理の集合 | `up` は 5 つ（不足リポジトリの報告 → `./deploy` → token の配布 → 窓のタイトルの設定 → エディタの自動オープン）を行う。エディタの自動オープンを除く 4 つは番号 1 から `scale` までの全部に、エディタの自動オープンは 1 つの番号にだけ行う。`scale` は 2 つ（token の配布 → `./deploy`）を増やした番号にだけ行う。2 つのコマンドで集合も順序も違う（`lib/devbase/commands/container.py` の `cmd_up` / `cmd_scale`） |
| 対象の渡し方 | 不足リポジトリの報告と窓のタイトルの設定は台数（`scale`）だけを受け、番号 1 から全部に行う。token の配布は開始の番号、`./deploy` は番号の並びを受ける。4 つで形が揃っていない |
| 起動の待ち | `wait_for_containers_ready`（`lib/devbase/utils/docker.py`）は番号 1 から順に状態を見て、終了した（`exited` / `dead`）か見つからない 1 台に当たった時点で、その 1 台の名前とログの末尾 10 行を載せた例外を投げる。ほかのインスタンスの完了を待たず、2 台以上が落ちていても最初の 1 台しか出ない。制限時間（60 秒）が切れたときの文言は `Timeout (60s) waiting for containers to be ready` で、どのインスタンスかは出ない |
| 待ちが失敗したとき | `up` は `Deploy failed: ...` を出して終了コード 1 で終わり、起動の後の処理 5 つをすべて飛ばす。`scale` は `Scale failed: ...` で 1 で終わり、2 つを飛ばす。どちらも起動できたインスタンスは動いたまま残る。`scale` はこの時点で `project.yml` の `scale` を書き換えてある（`tests/commands/test_container_scale_order.py` が現状として固定している） |
| 落ちたインスタンスを起こし直す道 | `docker start` では起動の後の処理が走らない。`devbase up` を打ち直すと、動いているインスタンスも含めて全部を止めて作り直す。`scale` が失敗した後の `devbase scale <同じ数>` は、`project.yml` が書き換わっているため `New scale (N) is not greater than current scale (N)` で断られる |
| 処理だけをやり直す手段 | token の配布は `devbase env token`（動いている dev のコンテナ全部へ配る）、エディタは `devbase open` がある。不足リポジトリの報告・窓のタイトルの設定・`./deploy` には、コンテナを作り直さずにやり直す手段が無い |
| 窓のタイトルが残る場所 | コンテナの中の `~/.vscode-server/data/Machine/settings.json`。`~/.vscode-server` はプロジェクトと番号ごとのボリュームである。新しいプロジェクトの番号と、`scale` で初めて作る番号はボリュームが空のため、窓のタイトルの設定が行われない限りタイトルが無い（#371 の再現と一致する） |
| 個々の処理の失敗の扱い | どの処理も `up` / `scale` を倒さない。不足リポジトリの報告は問い合わせに失敗すると何も出さない。`./deploy` と token の配布は警告を出す。窓のタイトルの設定は debug のログにだけ出す |

## 前提

- 前提 1: `up` の起動の後の処理の並びは変えない。`scale` はその並びからエディタの自動オープンを除いた 4 つ（インスタンスごとの処理）を同じ順に行う。今の `scale` は token の配布 → `./deploy` の順で、変更の後は `./deploy` → token の配布になる
- 前提 2: `scale` の後処理の対象は、増やしたインスタンスに限る。既存のインスタンスは、`up` か前の `scale` で処理が済んでいるものとして扱う
- 前提 3: `scale` はエディタを開かない（今のまま）
- 前提 4: 起動できたかどうかは、起動の待ちが今使っている 2 つの印（コンテナの状態と、コンテナの中の `/tmp/entrypoint-ready`）で決める。制限時間（60 秒）は変えない
- 前提 5: 起動の後の処理の 1 つ 1 つが失敗したときの扱い（警告か無言で続け、終了コードへ反映しない）は変えない
- 前提 6: `docker compose up` そのものが非 0 で終わったときの扱いは変えない（`up` は `Deploy failed`、`scale` は `Failed to start new containers` を出し、起動の後の処理を行わずに終了コード 1 で終わる）
- 前提 7: 接続先（docker context）の扱いは変えない。起動の後の処理は、`up` / `scale` が解決した接続先で動く
- 前提 8: 起動できなかったインスタンスを、devbase が自動で起こし直すことも、起動をやり直すこともしない
- 前提 9: 自動のテストは、今の `tests/commands/` と同じく、実物の docker と実物の `DEVBASE_ROOT` に触れない。実物の docker での確認は使い捨てのプロジェクトで行い、利用者のプロジェクトとボリュームに触れない
- 前提 10: 案 B の「処理だけをやり直す手段」は `./deploy` を走らせない。`./deploy` はプロジェクトが書くスクリプトで、2 回走らせて同じ結果になるとは限らないためである（未決 3）

## 対象範囲

含む:
- `devbase scale` が、増やしたインスタンスへ不足リポジトリの報告と窓のタイトルの設定を行うこと（#224）
- `up` と `scale` の起動の後の処理を、同じ並びにすること（前提 1）
- 起動できなかったインスタンスがあるときの `up` / `scale` の出力（名前・理由・補い方）と終了コード（#371）
- 起動できなかったインスタンスがあるときに、起動できたインスタンスの起動の後の処理が欠けたままにならない道を用意すること（#371。案 A か案 B か両方かは未決 1）
- 利用者向けの文書（CLI リファレンスの `up` と `scale` の節・環境変数ガイドの「ウィンドウタイトル」の節）と `CHANGELOG.md` の更新

含まない:
- 同時起動で 1 台が落ちる原因そのもの（#357）
- 起動できなかったインスタンスを devbase が自動で起こし直す仕組み（前提 8）
- `docker compose up` そのものが失敗したときの後処理（前提 6）
- 起動の後の処理の 1 つ 1 つが失敗したときの見せ方（前提 5。窓のタイトルの設定の失敗が debug のログにしか出ないことを含む）
- 既存のインスタンスへの `scale` の後処理（前提 2）
- `scale` が途中で失敗しても `project.yml` の `scale` が書き換わったまま残ること（`docs/specifications/compose-profiles.md` に書かれた今の振る舞い）
- `devbase project profile up` が走らせる `./deploy`（プロファイルのサービスの経路で、dev のインスタンスの起動を伴わない）
- `devbase scale` の実環境での確認そのもの（#246。この変更の後処理は #246 で併せて見られる）
- 設計の成果物のうち画面の図（変えるのはコマンドの出力の行だけで、画面を持たない）

| E10 | 窓のタイトルを設定した | E9 の後。`DEVBASE_WINDOW_TITLE` で止めていないときだけ | 書けない → debug のログに出して続ける（前提 5） | E9 |
| E11 | エディタを開いた | E10 の後。`up` で、自動オープンが有効なときだけ | 開けない → 警告して続ける（前提 5）。開く番号のインスタンスが起動できなかった → 受け入れ条件 A3 | E10 |
| E12 | 結果を報告して終えた | E11 の後（`scale` は E10 の後） | 起動できなかったインスタンスがある → 名前・理由・補い方を出して終了コード 1（受け入れ条件 10〜18） | E6 |
| E13 | 利用者が、落ちたインスタンスを起こし直した | 利用者の操作（`docker start` など）。**devbase の外で起きるため、起動の後の処理の引き金にならない** → 受け入れ条件 15・案 B | — | E12 |
| E14 | 起動の後の処理をやり直した（案 B） | 利用者が「処理だけをやり直す手段」を実行した | 動いているインスタンスが無い → 何も行わず非 0（受け入れ条件 B4） | E12。E13 の前でも後でもよい |

## 用語

| 用語 | 意味 |
| --- | --- |
| 起動の後の処理 | `up` と `scale` が、起動の待ちの後にホストの側から行う処理の並び。不足リポジトリの報告・`./deploy` の実行・token の配布・窓のタイトルの設定・エディタの自動オープンの 5 つ |
| インスタンスごとの処理 | 起動の後の処理のうち、インスタンスの 1 つ 1 つに行う 4 つ（エディタの自動オープンを除いたもの） |
| 起動の待ち | `up` と `scale` が、起動したインスタンスの entrypoint の完了を、制限時間まで待つ段 |
| 起動できたインスタンス | 起動の待ちで、entrypoint の完了を確かめられたインスタンス |
| 起動できなかったインスタンス | 起動の待ちの間に終了した・見つからない・制限時間までに entrypoint の完了を確かめられなかった、のどれかに当たるインスタンス |
| 増やしたインスタンス | `devbase scale` が足した番号のインスタンス（前の `scale` の値 + 1 から、新しい `scale` の値まで） |
| 後処理の対象 | インスタンスごとの処理を行うインスタンスの集合。`up` は起動できたインスタンス、`scale` は増やしたインスタンスのうち起動できたもの |
| 動いているインスタンス | 用語集のとおり（`docker ps` に現れる dev のインスタンス） |
| 開発サービス名 | 用語集のとおり（既定は `dev`。インスタンスは `<開発サービス名>-<番号>`） |
| 窓 | 用語集のとおり（dev のコンテナへ接続した VS Code のウィンドウ） |

## 受け入れ条件

読み方の決まり:

- 例は開発サービス名が `dev` のプロジェクトで書く。インスタンスは `dev-1`・`dev-2`・`dev-3` と呼ぶ
- 「インスタンスに処理が行われる」は、自動のテストでは、その処理がそのインスタンスの番号（またはコンテナ名）を対象に呼ばれることで確かめる。実物の docker では、コンテナの中の `~/.vscode-server/data/Machine/settings.json` の `window.title`・`~/.vault-token`・コマンドの出力で確かめる
- 案 A・案 B の節は、未決 1 で採ると決めた案の分だけが完了の条件になる。採らなかった案の条件は、消さずに取り消し線で残す

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 起動の待ちの制限時間（60 秒）を超えて待たない。全インスタンスが起動できたとき、待ちの 1 巡で docker を呼ぶ回数はインスタンスあたり 2 回（状態の確認と完了の確認）を超えない。案 A を採るとき、1 台が落ちた `up` / `scale` が終わるまでの時間は、残りのインスタンスの完了を待つ分だけ延びる（最長で制限時間まで。今は落ちた時点で終わる） |
| 運用・保守性 | 起動できなかったインスタンスごとに、名前と理由（終了した・見つからない・時間切れ）が出力に出る。利用者は出力だけで、どのインスタンスの何が欠けたかと、次に打つコマンドを読み取れる |
| セキュリティ | token を書く先は、後処理の対象（案 B の手段では、対象のプロジェクトの動いているインスタンス）に限る。token の値を、出力・ログ・`docker exec` の引数・コンテナの環境変数に載せない（今のまま） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 案 B を採るとき、コマンドかオプションが 1 つ増える（形は未決 2）。既存のコマンド・オプション・環境変数・compose の生成物は変わらない。全インスタンスが起動できたときの `up` / `scale` の終了コードと完了の行は変わらない |
| データ | スキーマの変更も移行も無い。`scale` で増やしたインスタンスのボリュームの `~/.vscode-server/data/Machine/settings.json` に `window.title` が書かれるようになる |
| 既存の振る舞い | (1) `scale` が、増やしたインスタンスへ不足リポジトリの報告と窓のタイトルの設定を行う。(2) `scale` の `./deploy` と token の配布の順が入れ替わる（前提 1）。(3) 起動できなかったインスタンスがあるときの出力が変わる（全部の名前・理由・補い方）。(4) 案 A を採るとき、起動できたインスタンスへは `./deploy` を含む後処理が行われ、1 台が落ちた `up` / `scale` は残りの完了を待ってから終わる。利用者に見える変更のため `CHANGELOG.md` に書く |
