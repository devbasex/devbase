# #357: 同じアカウントグループのコンテナを同時に起動すると entrypoint の symlink 作成が競合して 1 つが落ちる

正は課題の本文（#357）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 依頼（原文）

起票時の本文をそのまま写す。グループの実名だけは `<グループ>` に置き換えた（公開のリポジトリに固有の名前を置かない決まりのため）。

> ## 何を見つけたか
>
> 同じアカウントグループのコンテナを同時に起動すると、グループボリュームの symlink を張る処理が競合し、1 つが `ln: Already exists` で終了する（終了コード 1）。
>
> - 再現（2026-09-30）: ホストの再起動の後、グループ `<グループ>` の 4 コンテナ（プロジェクトが別々で `devbase_home_<グループ>` を共有）を `docker start` で同時に起動した。3 つは起き、1 つが次のログで落ちた
>
>   ```text
>     Creating symlink: /persistent/group/.claude/settings.json -> /persistent/ai/.claude/settings.json
>   ln: Already exists
>   ```
>
> - 落ちたコンテナをもう一度 `docker start` すると `✓ (symlink exists)` の経路で起きる（他のコンテナが同じ symlink を張り終えているため）
>
> ## 原因（推定）
>
> `containers/base/entrypoint.sh` の `devbase_link_setting()` は「symlink が正しいか見る → 違えば消す → `ln -s`」を排他なしで行う。2 つのプロセスが同時に「違う」と判定すると、後から `ln -s` した方が既存のリンクに当たって失敗し、`set -e` で entrypoint ごと終わる。
>
> ## 直すこと
>
> - `ln -s` を冪等にする（例: 一時名で作って `mv -T` で置き換える、または `ln -sfn` にして失敗の後に読み直す）か、グループボリュームの上で `flock` を取る
> - 同時に 2 つ走らせても両方が成功するテストを足す
>
> ## 対象外
>
> - ホストの再起動の後にコンテナを自動で起こす仕組み

## 目的

- ボリュームを共有するコンテナを同時に起動しても、すべてのコンテナが起動し、共有のリンクが正しい状態で残る
- 落ちたコンテナを利用者が見つけて起こし直す手間（今の回避策）を無くす

## 現状（2026-10-02 に調べたこと）

原文の推定を、コードと実環境の読み取りで確かめた。

| 調べたこと | 結果 |
| --- | --- |
| 競合する場所 | `devbase_link_setting()` が張るリンクのうち、複数のコンテナが同じ 1 本を使うのは共有のリンク 5 本（`/persistent/group/.claude/` の `plugins` / `skills` / `commands` / `CLAUDE.md` / `settings.json`）だけである。ホーム直下のリンクはコンテナごとに別で、競合しない |
| 競合が起きる条件 | リンクの段が共有のリンクを張り直すとき。実環境では `settings.json` が運用中に通常のファイルへ置き換わっており（#372）、9 コンテナの起動 16 回のうち 11 回で張り直していた。新しいグループのボリュームの初回は 5 本とも張る |
| 落ちたときのログ | 落ちた 2 件とも、`Removing existing ...` の行が無いまま `Creating symlink: ...` → `ln: Already exists` で終わっていた（相手が実体を消した後、相手より遅く `ln -s` した） |
| 再現のしやすさ | `devbase_setup_ai_settings` を、別々のホーム・同じ 2 つのボリューム（`settings.json` が通常のファイル）へ向けて 4 個同時に走らせると、20 回のうち 20 回で 1 個以上が非 0 で終わった（macOS・bash 5.3・Docker なし） |
| base イメージの道具 | 動いているコンテナ（Ubuntu 26.04）では `ln` が uutils coreutils 0.8.0、`mv` が GNU coreutils 9.7 で、`flock` が入っている。失敗の文言 `Already exists` は uutils の `ln` のもの（GNU は `File exists`） |
| 同じ競合のほかの入口 | scale 2 のプロジェクトを新しく足した `devbase up` でも 2 台目が同じ形で落ちた（#371 の再現）。ホストの再起動に限らない |

## 前提

- 前提 1: 修正は base イメージの建て直しでコンテナへ届く。派生イメージとプロジェクトのイメージは別々に建て直すため、同じグループに修正前と修正後のイメージのコンテナが並ぶ期間がある
- 前提 2: 同時起動の数は 8 個までを確かめる（観測した最大は 1 グループ 4 個）。8 個を超える数は確かめない
- 前提 3: リンクの位置に実体（通常のファイル・ディレクトリ・別の先を指すリンク）があるときは、消して張り直す。この決まりは変えない（是非は #372 で決める）
- 前提 4: 競合の相手として扱うのは、ほかのコンテナのリンクの段だけである。動いているコンテナの中のツールが同じ位置へ書くこととの競合は、受け入れ条件に入れない
- 前提 5: base イメージに道具を足さず、道具の版も変えない。今のイメージに入っている道具だけで実現する
- 前提 6: テストは今の `tests/containers/test_entrypoint_ai_settings.py` と同じく、Docker を使わずに entrypoint の関数を一時ディレクトリへ向けて走らせる。CI（Linux）では必ず走る。開発者の macOS で走れないテストは、理由を示して skip する

## 対象範囲

含む:
- 共有のリンクを張る処理が、同時起動で失敗しないこと
- リンクの段の全体（ボリュームのルートの用意・イメージの設定の退避・プレースホルダの作成・リンク）を同時に走らせた結果が、1 つずつ順に走らせた結果と同じになること
- 同時に走らせて確かめるテストを足すこと
- 修正前のイメージのコンテナと並んで起動したときに、修正後のコンテナが落ちないこと

含まない:
- ホストの再起動の後にコンテナを自動で起こす仕組み（原文の対象外）
- リンクの位置に実体があるときに消して張り直す決まりの是非と、`settings.json` の置き場（#372）
- `devbase up` / `devbase scale` で 1 台が落ちたときの後処理（#371・#224）と、落ちたコンテナを起こし直す仕組み
- 修正前のイメージのコンテナが落ちること（建て直すまで今の振る舞いのまま残る）
- リンクの段の外の entrypoint の処理（Git・AWS・GCP の資格情報、リポジトリの clone、Docker-in-Docker）の同時実行
- 動いているコンテナの中のツールとの競合（前提 4）
- 設計の成果物のうちクラス図（変えるのは bash の関数で、型を持たないため、描く対象が無い）

## 用語

| 用語 | 意味 |
| --- | --- |
| アカウントグループ | 用語集のとおり（`DEVBASE_ACCOUNT_GROUP` の値） |
| グループのボリューム | 用語集のとおり（コンテナの `/persistent/group`） |
| 共通のボリューム | すべてのコンテナが `/persistent/ai` にマウントする 1 つのボリューム。グループをまたいで共有する |
| 共有のリンク | グループのボリュームの `.claude` の下にあり、共通のボリュームの同じ名前のエントリを指す symlink。`plugins` / `skills` / `commands` / `CLAUDE.md` / `settings.json` の 5 本。同じグループのすべてのコンテナが同じ 1 本を使う |
| リンクの段 | entrypoint が AI 設定のリンクを張る処理（`devbase_setup_ai_settings` の 1 回の実行） |
| 同時起動 | 2 つ以上のコンテナのリンクの段が、時間の上で重なって走ること |
| 修正前の手順 | この変更より前のリンクの張り方。「正しいかを見る → 違えば消す → `ln -s`」を、ほかのコンテナを待たずに行う |

## 受け入れ条件

「同時に走らせる」は、別々のホームと、同じ共通のボリューム・同じグループのボリュームを渡したリンクの段を、同時に始めることを指す。

- [ ] 1. 前提: 共有のリンクのうち `settings.json` だけが通常のファイルで、残り 4 本は正しい
      操作: リンクの段を 2 個同時に走らせる
      結果: 2 個とも終了コード 0 で終わり、`settings.json` は共通のボリュームの `settings.json` を指す symlink になる
- [ ] 2. 受け入れ条件 1 と同じ前提で 8 個同時に走らせると、8 個とも終了コード 0 で終わり、共通のボリュームの `settings.json` の中身は走らせる前と同じである
- [ ] 3. 前提: 共通のボリュームもグループのボリュームも空で、どのホームにも同じ中身の `~/.claude/settings.json` がある
      操作: リンクの段を 8 個同時に走らせる
      結果: 8 個とも終了コード 0 で終わる。2 つのボリュームのファイルとディレクトリの並び・リンクの先・ファイルの中身が、同じ前提で 1 個だけ走らせたときと同じになる
- [ ] 4. 前提: 共通のボリュームに中身があり、グループのボリュームが空である
      操作: リンクの段を 8 個同時に走らせる
      結果: 8 個とも終了コード 0 で終わり、共有のリンク 5 本がそれぞれ共通のボリュームの同じ名前のエントリを指す
- [ ] 5. 共有のリンク `plugins` の位置に、中にファイルを持つ実体のディレクトリがある状態で 8 個同時に走らせると、8 個とも終了コード 0 で終わり、`plugins` は共通のボリュームを指す symlink になる
- [ ] 6. 共有のリンクの 1 本が別の先を指している状態、指す先の無い壊れたリンクである状態のそれぞれで 8 個同時に走らせると、8 個とも終了コード 0 で終わり、そのリンクは共通のボリュームを指す
- [ ] 7. 修正後のリンクの段 1 個と、同じ共有のリンクを修正前の手順で張る相手 1 個を同時に走らせると、修正後の側は終了コード 0 で終わり、共有のリンクは共通のボリュームを指す（相手が非 0 で終わることは許す）
- [ ] 8. 受け入れ条件 1〜6 の同時に走らせるテストは、修正前の `entrypoint.sh` に当てると失敗する（受け入れ条件 1 か 2 のテストを 3 回続けて走らせ、3 回とも失敗する）
- [ ] 9. グループのボリュームの `.claude` に書き込めない状態でリンクの段を走らせると、非 0 で終わり、張れなかったリンクのパスを含む行が出る（同時起動の競合ではない失敗を、成功として扱わない）
- [ ] 10. 受け入れ条件 1〜7 で終了コード 0 で終わったリンクの段の出力に、`ln:` で始まる行が無い
- [ ] 11. 受け入れ条件 1〜7 のあと、グループのボリュームの `.claude` の下に、張り替えの途中で使う一時的な名前のエントリが残っていない
- [ ] 12. 既存の `tests/containers/test_entrypoint_ai_settings.py` の 35 件が、テストを書き換えずに通る
- [ ] 13. 前提: base イメージ（`ln` が uutils coreutils のもの）と修正後の `entrypoint.sh`、使い捨ての共通のボリュームとグループのボリューム（受け入れ条件 1 の状態にしたもの）
      操作: 8 個のコンテナを同時に起動する
      結果: 8 個とも entrypoint が終了コード 0 で終わる。利用者のボリュームには触れない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | ほかのコンテナを待つ仕組みを使う場合、待たせている側のプロセスが途中で kill されても、後から始めたリンクの段は 30 秒以内に終了コード 0 で終わる。kill の後に残ったもの（一時的な名前のエントリなど）があっても、次のリンクの段は終了コード 0 で終わる |
| 性能・拡張性 | 8 個同時に走らせたとき、8 個すべてが 30 秒以内に終わる（手元と CI）。1 個だけで走らせたときの所要は、修正前の所要に 1 秒を足した値を超えない。8 個を超える同時起動は確かめない（前提 2） |
| 移行性 | 修正前と修正後のイメージのコンテナが同じグループに並ぶ（前提 1）。修正後のリンクの段がボリュームに残すものは、修正前の手順のリンクの段を失敗させない（並走のときも、entrypoint を前の版へ戻したときも）。ボリュームのデータの移行は無い |
| システム環境 | base イメージに今入っている道具だけで動く（前提 5）。テストは Linux の CI で走る（前提 6） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない（コマンド・環境変数・compose の生成物）。起動ログの `✓ ... (symlink exists)` と `Creating symlink: ...` の行の形は保つ |
| データ | スキーマの変更も移行も無い。共有のリンクの指す先は変わらない |
| 既存の振る舞い | 同時起動で落ちなくなる。効くのは base イメージを建て直したコンテナからである。利用者に見える変更のため `CHANGELOG.md` の `[Unreleased]` の `Fixed` に書く |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `env -u DEVBASE_ROOT uv run --locked pytest tests/containers/ -q`（全体は `.ndf/project.json` の `test.suites` のコマンド） |
| 静的解析・型検査 | `shellcheck containers/base/entrypoint.sh`（CI の ShellCheck の検査ジョブと同じ版 v0.11.0）、`uv run ruff check tests/` |
| 起動 | 受け入れ条件 13。`docker run` で、使い捨ての名前のボリューム 2 つとコンテナ 8 個を作り、終了コードを集めてから消す。`devbase up` は使わない |
| 手動確認 | 無し（人にしか見られない条件は無い） |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | entrypoint の関数は `containers/base/entrypoint.sh` の中で、`DEVBASE_ENTRYPOINT_LIB_ONLY` の `return` より前に置く（テストが関数だけを読み込むため）。テストは `tests/containers/` に置く。`lib/devbase` の起動の側（`up` / `scale`）は触らない |
| コーディング規約 | `CONTRIBUTING.md`。シェルは CI の ShellCheck の検査ジョブ、Python は Ruff で確かめる |
| テスト戦略 | 関数の水準（Docker なし）で、同時起動と状態の境界（受け入れ条件 1〜12）を固定する。実物のコンテナでは、base イメージの道具で動くこと（受け入れ条件 13）を完了判定で 1 回確かめる |
