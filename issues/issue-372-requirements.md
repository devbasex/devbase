# #372: グループのボリュームの .claude/settings.json が運用中に symlink から通常のファイルへ置き換わり、次の起動で消されて張り直される

正は課題の本文（#372）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 依頼（原文）

> 以下は起票したときの本文である（要約しない）。

> ## 何を見つけたか
>
> グループのボリュームの `.claude/settings.json`（コンテナの `/persistent/group/.claude/settings.json`）は、entrypoint が共通側 `/persistent/ai/.claude/settings.json` への symlink として張る。ところが運用中に **symlink が通常のファイルへ置き換わり**、次の起動で entrypoint がそのファイルを消して symlink を張り直している。
>
> 観測（2026-10-02 01:00 UTC 頃、1 台の端末、3 グループ・動いている 9 コンテナ。読み取りだけで確かめた）:
>
> | 見たもの | 結果 |
> | --- | --- |
> | `/persistent/group/.claude/settings.json` の種別（`stat`） | 3 グループのうち 2 グループで通常のファイル、1 グループで symlink |
> | 通常のファイルになっていた 2 グループの中身（SHA-256 を共通側と比べた） | 1 グループは共通側と一致、1 グループは**不一致**（大きさは同じ 7279 バイト） |
> | 同じ `.claude` の下の `plugins` / `skills` / `commands` / `CLAUDE.md` | symlink のまま |
> | 9 コンテナの起動ログ（起動 16 回） | `Removing existing /persistent/group/.claude/settings.json...` が 10 回、`Creating symlink: /persistent/group/.claude/settings.json` が 11 回 |
>
> あるグループでは、起動で symlink を張り直した時刻より後に、同じ位置が通常のファイルへ変わっていた（張り直しから数時間後の更新時刻）。
>
> 中身が共通側と食い違っていたグループのファイルは、同じ日の起動の張り直しで消えており、その差は既に失われている。2026-10-02 18:20 UTC 時点では、動いている 10 コンテナのすべてで同じ位置が symlink（張り直しは 10:25〜11:21 UTC）で、共通側の `settings.json` の更新時刻は 00:32 UTC だった。
>
> 誰が置き換えるかは**確かめていない**。`~/.claude/settings.json` へ書くツールが「一時ファイルへ書いて rename する」形で保存すると、symlink そのものが通常のファイルに置き換わる。この見込みを最初に確かめる。手がかりは次の 2 つである。
>
> - symlink を通して中身を書き換えたなら、共通側の更新時刻が進み、グループ側は symlink のまま残る
> - rename で置き換えたなら、共通側の更新時刻は進まず、グループ側が通常のファイルになり、その更新時刻が書いた時刻を示す。同じ時刻に動いていたツールと突き合わせる
>
> ## どこで見つけたか
>
> - `containers/base/entrypoint.sh` の `devbase_link_setting()`（372 行。link の位置に実体があれば `rm -rf` して張り直す）と、`DEVBASE_SHARED_CLAUDE_SETTINGS`（223 行。`settings.json` を共通側へ張る一覧）
> - issue #357 の要求を書くために、競合が起きる条件を実環境で調べたとき
>
> ## なぜこの変更の範囲外なのか
>
> issue #357 が扱うのは「同時に起動しても落ちないこと」で、link の位置に実体があるときに消して張り直すという決まりは変えない。この課題は、その決まりと `settings.json` の置き場そのものを問う。
>
> 根拠: Value 2（作り直しで失わない）に関わるが、#357 の受け入れ条件の外にある（MVV 版 1）。
>
> ## 直さないと何が起きるか
>
> - グループ側の通常のファイルに書かれた設定（hooks・permissions など）が、次の起動で消えて共通側の内容へ戻る。上の観測では 1 グループで中身が共通側と食い違っており、その差は次の起動で失われた
> - 起動のたびに symlink の張り直しが走る。同じグループの同時起動で 1 台が落ちることは #357 の flock と読み直しで起きなくなった（`issues/issue-311-operation.md` の R3 で、通常のファイルを置いた状態で 3 台を同時に起こし直し、3 台とも動き続けた）。張り直しそのものと、それに伴う設定の消失は続く
>
> ## 決めること（見込み）
>
> - 誰が symlink を通常のファイルへ置き換えているかを特定する
> - `settings.json` を全グループ共通に保つのか、グループごとに持つのかを決める
> - 共通に保つなら、通常のファイルが見つかったときに中身を捨てるのか、共通側へ取り込むのかを決める
>
> ## 由来
>
> issue #357
>

## 調査の結果（要求を書くときに読み取りだけで確かめたこと）

| 見たもの | 結果 |
| --- | --- |
| NDF（ai-plugins）の SessionStart の hook | `ensure-retention.sh`（`cleanupPeriodDays` を 90 日以上に保つ）と `statusline-switch.sh ensure`（`statusLine` を補う）が、起動のたびに `~/.claude/settings.json` へ書くことがある |
| 2 つのスクリプトの書き方（10.17.50 まで） | `SETTINGS="$CONFIG_DIR/settings.json"` へ `jq ... > "$tmp"; mv "$tmp" "$SETTINGS"` で書く。コンテナでは `~/.claude` がグループのボリュームの `.claude` を指すので、`mv` は共有のリンクを通常のファイルで置き換える |
| 同じスクリプト（10.17.51 から。公開は 2026-10-01 13:03 UTC） | `lib/claude-settings.sh` の `claude_settings_path` が、`settings.json` が symlink なら `readlink -f` の先へ書く（ai-plugins#1576 の決定 14）。共有のリンクを置き換えない |

起票の観測（2026-10-02 01:00 UTC 頃）は 10.17.51 の公開から約 12 時間後で、動いていたセッションには 10.17.50 以前の hook が残っていた見込みが高い。大きさが同じで中身が違ったグループは、`statusLine` などの値の一部が同じ長さの別の値へ変わった形と合う。ただし、置き換えた時刻のセッションと版の突き合わせは、ファイルが既に消えているためできない。

Claude Code 本体（`/model`・`/permissions`・`/plugin` などで利用者の `settings.json` へ書く）が symlink を保って書くかは確かめていない（未決 1）。

## 目的

- 共有のリンクが通常のファイルへ置き換わっても、次の起動でその中身を黙って失わない（Value 2）
- 置き換わったことを、利用者が起動の記録から知れる
- `settings.json` は全グループで共通の 1 つに保ち、グループの設定を確認なしに共通のボリュームへ持ち込まない（Value 3）

## 前提

- 前提 1: `settings.json` は今の設計のとおり全グループ共通に保つ。グループごとの `settings.json` の置き場は作らない。根拠: `docs/user/container-operations.md` が `settings.json` を「契約やテナントに紐づかない共通資産」と定めており、グループごとに持つのはこの課題の範囲を超える設計の変更である
- 前提 2: 置き換わった共有のリンクの中身は、共通のボリュームへ自動で取り込まない。グループのボリュームに共有のリンクの控えとして残し、取り込むかは利用者が決める。根拠: 自動で取り込むと、あるグループで書いた設定（hooks・permissions など）が確認なしに全グループへ広がる（Value 3）
- 前提 3: 中身が共通のボリュームの実体とバイト単位で同じなら、控えを作らずに張り直す。失う中身が無いためである
- 前提 4: 対象は共有のリンクのうち**ファイル**のエントリ（`settings.json` と `CLAUDE.md`）に限る。`plugins` / `skills` / `commands` はディレクトリで、起票の観測では置き換わっていない
- 前提 5: 置き換えの主の候補は上の「調査の結果」の NDF の hook で、ai-plugins 10.17.51 で直っている。devbase の側では置き換えを防がず、置き換わった後に失わないことを受け持つ。書き手を 1 つずつ塞いでも、別のツールが同じ書き方をすれば再び起きるためである
- 前提 6: 控えは自動で消さない。数が増えたときに消すのは利用者である（同じ中身の控えを何度も作らない条件は受け入れ条件 4 に置く）

## 対象範囲

含む:

- リンクの段が、共有のリンクの位置に通常のファイルを見つけたときの扱い（同じ中身なら張り直す、違えば控えを残して張り直す）
- 起動の記録（コンテナのログ）への知らせ
- 確定仕様 `docs/specifications/container-link-stage.md` と利用者向けの `docs/user/container-operations.md` への、控えの置き場と戻し方の追記
- 置き換えの主を特定した結果の記録（この課題の本文の「調査の結果」と、未決 1 を確かめた結果）

含まない:

- `settings.json` をグループごとに持つ置き場を作ること（前提 1）
- 控えの中身を共通のボリュームへ自動で取り込むこと・JSON をマージすること（前提 2）
- NDF（ai-plugins）や Claude Code の書き方を直すこと（前提 5。必要なら各リポジトリへ起票する）
- `plugins` / `skills` / `commands` などディレクトリの共有のリンク（前提 4）
- ホーム直下のリンク（`~/.claude` など分類 B）の扱い
- 同時起動の扱いを変えること（#357 で決めたリンクの段のロックと張り替えの試行はそのまま使う）

## ドメインイベント

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | 共有のリンクが通常のファイルへ置き換わった | コンテナの中のツールが `~/.claude/settings.json` へ一時ファイルの rename で書いた | — （devbase の外で起きる） | 共有のリンクが張られている |
| E2 | リンクの段が、共有のリンクの位置に通常のファイルを見つけた | コンテナの起動（entrypoint） | — | E1 |
| E3 | 中身を共通のボリュームの実体と比べた | E2 | 読めない（権限・壊れた実体）ときは「違う」として扱い、E4 へ進む | E2 |
| E4 | 置き換わった共有のリンクを控えとして残した | E3 で中身が違った | 控えを作れないときは元のファイルを消さず、張り直さずに警告を出して起動を続ける | E3 |
| E5 | 共有のリンクを張り直した | E3 で同じ、または E4 が終わった | #357 の張り替えの試行に従う | E3 か E4 |
| E6 | 起動の記録に控えの場所を知らせた | E4 | — | E4 |

同時起動のときは、E2〜E6 はリンクの段のロックの中で 1 つのコンテナだけが行い、ほかのコンテナは張り直された共有のリンクを見る（#357）。

## 用語

| 用語 | 意味 |
| --- | --- |
| 置き換わった共有のリンク | 共有のリンクの位置にある、symlink ではない通常のファイル |
| 共有のリンクの控え | 置き換わった共有のリンクの中身を、張り直す前にグループのボリュームの同じ `.claude` の下へ別の名前で残したファイル |

## 受け入れ条件

- [ ] 1. 前提: グループのボリュームの `.claude/settings.json` が通常のファイルで、中身が共通のボリュームの `.claude/settings.json` とバイト単位で同じ
      操作: リンクの段を走らせる
      結果: `.claude/settings.json` が共通のボリュームの実体を指す symlink になり、控えのファイルは 1 つも作られない
- [ ] 2. 前提: グループのボリュームの `.claude/settings.json` が通常のファイルで、中身が共通のボリュームの実体と違う
      操作: リンクの段を走らせる
      結果: `.claude/settings.json` が共通のボリュームの実体を指す symlink になり、同じ `.claude` の下に `settings.json.replaced-<UTC の時刻 YYYYmmddTHHMMSSZ>` が 1 つでき、その中身・所有者・権限は置き換わっていたファイルと同じである
- [ ] 3. 条件 2 のとき、コンテナのログ（標準エラー）に `WARNING:` で始まる行が出て、その行に控えのパスが含まれる。条件 1 のときはこの行が出ない
- [ ] 4. 前提: 条件 2 の控えが既にあり、同じ中身の通常のファイルが再び共有のリンクの位置にある
      操作: リンクの段を走らせる
      結果: 新しい控えは作られず、共有のリンクが張り直される（同じ中身の控えを 2 つ作らない）
- [ ] 5. `CLAUDE.md` についても、条件 1〜4 と同じ結果になる（控えの名前は `CLAUDE.md.replaced-<時刻>`）
- [ ] 6. 控えを作れない（書き込めない）とき、置き換わった共有のリンクは消されずに残り、`WARNING:` の行が出て、リンクの段とコンテナの起動は失敗しない
- [ ] 7. 共通のボリュームの `.claude/settings.json` と `.claude/CLAUDE.md` の中身は、リンクの段の前後で変わらない（控えの中身を共通のボリュームへ書かない）
- [ ] 8. 同じグループのボリュームを使う 2 つのリンクの段を同時に走らせたとき（条件 2 の前提で始める）、控えはちょうど 1 つでき、共有のリンクは symlink で終わる
- [ ] 9. 共有のリンクが既に正しい symlink のとき、リンクの段の出力と結果は変更の前と同じである（控えも `WARNING:` も出ない）
- [ ] 10. `docs/specifications/container-link-stage.md` と `docs/user/container-operations.md` に、控えの名前・置き場・知らせの出る場所と、利用者が中身を共通のボリュームへ戻す手順が書かれている
- [ ] 11. 未決 1 を確かめた結果（Claude Code 本体が symlink を保って書くか）が、この課題の本文か設計の文書に、確かめた手順とともに記録されている。保たないと分かったときは、Claude Code への報告か devbase での対策を別の課題として起票してある

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 控えの作成に失敗してもコンテナの起動は続く（受け入れ条件 6） |
| 運用・保守性 | 置き換わったことと控えのパスが、`docker logs` で読める起動の記録に残る（受け入れ条件 3） |
| 移行性 | 既存のボリュームはそのまま使える。効くのは base イメージを建て直した後のコンテナからで、建て直す前のイメージとは同じボリュームの上で並んで動いてもよい（古いイメージは今のとおり消して張り直す） |
| セキュリティ | 控えの所有者と権限は元のファイルと同じで、ほかの利用者に読める形へ広げない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない（コマンド・環境変数・compose の生成物を持たない） |
| データ | グループのボリュームの `.claude` の下に控えのファイルが増えることがある。共通のボリュームは変わらない |
| 既存の振る舞い | 共有のリンクの位置に中身の違う通常のファイルがあったとき、消さずに控えへ移す。それ以外は変わらない |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `uv run --locked pytest tests/containers -q` （entrypoint を `DEVBASE_ENTRYPOINT_LIB_ONLY=1` で source し、一時ディレクトリの 2 つのボリュームで確かめる。Docker に依存しない） |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | 変更は `containers/base/entrypoint.sh` のリンクの段に置く。起動する側（`bin/devbase`・`lib/devbase`）には置かない |
| コーディング規約 | `AGENTS.md`。シェルは ShellCheck を通す。記録や例に実在のグループ名・プロジェクト名を書かず、`team-a` などの中立の名前を使う |
| テスト戦略 | `tests/containers` の単体の階層で、リンクの段を一時ディレクトリに当てて確かめる（#357 の `test_entrypoint_ai_settings_concurrent.py` と同じ形）。コンテナを実際に起こす確認はリリース後テストに回す |
