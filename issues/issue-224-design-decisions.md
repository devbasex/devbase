# #224・#371: 決定の記録

設計の本体は [issue-224-design.md](issue-224-design.md) にある。この文書はその「決定の記録」の節である。
決定 1〜5 と決定 10 は、要求の未決 1〜6 への答えで、設計の Pull Request の承認で確定する。

## 決定の記録

### 決定 1: 起動できたインスタンスへ後処理を行ってから失敗として終え、加えて処理だけをやり直すコマンドを用意する

#371 が挙げた 2 つの直し方は、補う場面が違う。起動できたインスタンスへその場で後処理を行うと、利用者が何も
打たなくても、動いているインスタンスの token・窓のタイトル・`./deploy` が揃う。やり直しのコマンドは、落ちた
インスタンスを起こし直した後と、時間切れになったインスタンスが後から起動を終えた後に、動いているインスタンスを
作り直さずに処理を補う。両方を採ると、欠けたままになる場面が残らない。

| 場面 | その場で後処理を行うだけ | やり直しのコマンドだけ | 両方 |
| --- | --- | --- | --- |
| 1 台が起動できなかった直後の、起動できたインスタンス | 揃う | 利用者がコマンドを打つまで欠けたまま。`./deploy` は補えない | 揃う |
| 落ちたインスタンスを `docker start` で起こし直した後 | 補う道は `devbase up` の打ち直しだけ | コマンドで補える（`./deploy` を除く） | コマンドで補える（`./deploy` を除く） |
| 時間切れの後に起動を終えたインスタンス | 補う道は `devbase up` の打ち直しだけ | コマンドで補える（`./deploy` を除く） | コマンドで補える（`./deploy` を除く） |
| `scale` で増やした 1 台が起動できなかった後 | `devbase scale` は同じ数を断るため、`devbase up` の打ち直しになる | コマンドで補える（`./deploy` を除く） | コマンドで補える（`./deploy` を除く） |
| 公開インタフェース | 増えない | コマンドが 1 つ増える | コマンドが 1 つ増える |

その場の後処理だけにする形は採らなかった。残る道の `devbase up` の打ち直しは、動いているインスタンスを止めて
作り直すうえ、同時の起動で 1 台が落ちる競合（#357）では同じ競合へもう一度入る。やり直しのコマンドだけにする
形も採らなかった。利用者が打つまで token と窓のタイトルが欠けたままになり、`./deploy` を持つプロジェクトでは、
起動できたインスタンスの `./deploy` を補う道が `devbase up` の打ち直しだけになる。

要求の受け入れ条件は、「案 A」の節の A1〜A6 と「案 B」の節の B1〜B7 が完了の条件になる。B8 は、やり直しの
手段だけを採るときの条件のため当たらない。

根拠: Mission / Value 1（MVV 版 1）

### 決定 2: やり直しは新しいサブコマンド `devbase project post-start [name]` にし、`up` のオプションにしない

`up` は全インスタンスを止めて作り直すコマンドである。`up` にオプションを足す形は、付け忘れ 1 つで動いている
インスタンスが作り直されるため採らなかった。コンテナに触らずに窓を開き直す `devbase open` と同じく、コンテナに
触らない操作は別のコマンドにする。

名前は用語集のコンテキストの識別子（`post-start`）と同じ語にした。`re` で始まる名前（`refresh`・`reapply`）は、
今は `rebuild` に決まる前方一致（`project r`・`project re`）を曖昧にするため採らなかった。`post-start` は
`project p`（`ps`）と `project pr`（`profile`）の解決を変えない。

置き場は `project` グループだけにする。トップレベルの短縮形は日常の操作のためのもので、失敗の後にだけ打つ
コマンドは足さない。`container` グループは非推奨のため、新しいコマンドを足さない。TUI の操作の一覧にも足さない。

根拠: Mission / P3（MVV 版 1）

### 決定 3: やり直しは `./deploy` を走らせず、エディタも開かない

`./deploy` はプロジェクトが書くスクリプトで、2 回走らせて同じ結果になるとは限らない。やり直しの対象は
動いているインスタンスの全部で、`up` で既に `./deploy` が済んだインスタンスを含むため、走らせると済んだ
インスタンスで 2 回目が走る。番号を選んで `./deploy` を走らせるオプションは、要求に無いため足さない。
エディタは `devbase open` で開けるため、やり直しでは開かない。

根拠: Value 3（MVV 版 1）

### 決定 4: `scale` の `./deploy` と token の配布の順を、`up` に合わせて入れ替える

`up` の並び（`./deploy` → token の配布）を基準にすると、`up` の振る舞いが変わらない。変わるのは `scale` で
増やした分の `./deploy` だけで、token が配られた後ではなく前に走るようになる。同じ `./deploy` は `up` では
token の無い状態で走っているため、token があることを前提にできていない。`up` を `scale` の順へ合わせる形は、
すべての `up` で `./deploy` が見る状態を変えるため採らなかった。

根拠: 根拠なし（MVV 版 1）

### 決定 5: 開く番号のインスタンスが起動できなかったときは、エディタを開かず、ほかの番号へ替えない

開く番号は利用者が指定している（`--open-index` か `DEVBASE_OPEN_INDEX`。無ければ 1）。起動できた別の番号の
窓を開くと、利用者は指定と違うインスタンスで作業を始めることになる。開かなかったことは警告で伝える。
起こし直した後は `devbase open` で開ける。

根拠: Mission（MVV 版 1）

### 決定 6: 起動の待ちは引数と成功時の戻り値を変えず、起動できなかったものがあれば内訳を持つ例外を投げる

例外で返すと、失敗は既定で失敗のままになる。例外を受けない呼び出し元は、今と同じく失敗として終わる。
内訳を戻り値で返す形は、戻り値を見ない呼び出し元が部分的な失敗を成功として扱えてしまうため採らなかった。
起動の段（`_run_deploy_pipeline`・`_run_scale_pipeline`）の戻り値と、起動の待ちを差し替えている既存の
テストの組み（6 ファイル）も変えずに済む。

根拠: 根拠なし（MVV 版 1）

### 決定 7: 1 台が起動できなくても残りを制限まで待ち、決まったインスタンスへは問い合わせ直さない

待ちを 1 台目で打ち切ると、番号の小さい 1 台が落ちたときに、後から起動を終えるインスタンスが起動できたか
どうかが分からず、後処理を届けられない。代わりに、1 台が落ちた `up` / `scale` が終わるまでの時間は、最長で
制限まで延びる（要求の非機能の条件が認めている）。決まったインスタンスへ問い合わせ直さないのは、docker の
呼び出しを増やさないためである。起動できたと決まった後に終了したインスタンスは、個々の処理が今の扱いで飛ばす。

根拠: Value 1（MVV 版 1）

### 決定 8: 制限時間の数え方（巡の回数）を変えない

要求の前提 4 が、制限時間を変えないと定めている。今の制限は、1 秒の休みを挟む巡を 60 回という数え方で、
docker の呼び出しにかかる分だけ実際の時間は 60 秒を超える。実際の時間で数える形へ変えると、今は通っている
遅い起動（初回の clone が長い・接続先が遠い）が時間切れになり得るため、この変更では変えない。数え方は
#374 で扱う。

根拠: 根拠なし（MVV 版 1）

### 決定 9: 個々の処理の関数は、対象を受ける引数を足すだけにし、今の呼び出しの形も受ける

不足リポジトリの報告・token の配布・窓のタイトルの設定は、今は台数（token の配布は開始の番号も）を受ける。
対象の番号の並びを受けるキーワード引数を足し、渡されなければ今と同じ範囲に行う。これらの関数を直に呼んでいる
既存のテストが書き換えずに通り、個々の処理の振る舞いが変わっていないことの確かめになる。台数と開始の番号の
引数を外して対象だけを受ける形は、直に呼んでいる既存のテストの書き換えが受け入れ条件 23 の範囲を超えるため
採らなかった。

根拠: 根拠なし（MVV 版 1）

### 決定 10: 実物の docker では、印を置いた番号のインスタンスだけを終了させて確かめる

受け入れ条件 24 は、使い捨てのプロジェクト（台数 2）で確かめる。dev サービスの起動コマンドを包み、番号ごとの
ボリュームに印があるインスタンスだけを、完了の印より前に終了させる。決まった 1 台が必ず落ち、印を消してから
`docker start` で起こし直せるため、出力の手順をやり直しのコマンドまで通せる。同時の起動の競合（#357）に頼る
方法と、待ちの最中に手で `docker kill` を打つ方法は、落ちるかどうかが偶然と打つ時機に左右されるため採らなかった。
包みの具体の形（印を置くボリュームとパス）は、実装で走らせて決める。

`DEVBASE_ROOT` を一時ディレクトリへ向け、利用者のプロジェクトとボリュームに触れない。確かめた後に、使った
コンテナとボリュームを消す。

根拠: Value 3 / P3（MVV 版 1）

### 決定 11: やり直しは、動いていない番号があっても 0 で終わり、1 つも動いていなければ 1 で終わる

やり直しの役目は、動いているインスタンスへ処理を行い直すことである。動いていない番号があっても役目は
果たせるため 0 で終わり、その番号を警告で伝える。1 つも動いていないときは何も行えていないため 1 で終わる。
動いていないときに `devbase up` へ委ねて起動する形（`devbase open` の動き）は、devbase が起動をやり直さない
という要求の前提 8 と受け入れ条件 B4 に合わないため採らなかった。

根拠: 根拠なし（MVV 版 1）

### 決定 12: 起動できなかったときの報告は、後処理の後、出力の最後に出す

利用者は出力の末尾を読む。起動できなかった名前・理由・補う手順を、個々の処理の出力より後ろに置くと、
`./deploy` の出力に埋もれない。起動の待ちの直後には、後処理を続けるかどうかの警告を 1 行だけ出す。

根拠: 根拠なし（MVV 版 1）
