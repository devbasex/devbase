# #295: OpenBao backend を、利用者が個人・チームで自分のサーバを立てて使う前提の文書と雛形に揃える

正は課題の本文（#295）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何をしたいか

devbase の OpenBao backend を、**利用者が個人またはチームで自分の OpenBao サーバを立てて使う**前提で使えるようにする。

今の文書と設計は、ある 1 つの組織が運用しているサーバへ接続することを前提に書かれている。OSS として多くの人が使うなら、サーバの用意から devbase の接続までを、利用者が公開の情報だけで再現できる必要がある。

| 項目 | 内容 |

## 確かめること

- `openbao.url` を `http://127.0.0.1:8200` にしたとき、`devbase up` がコンテナへ渡す `BAO_ADDR`（`lib/devbase/commands/container.py:921-932` の `_bao_environment`）がコンテナの中から届くか。`_bao_environment` は `openbao.url` をそのまま `BAO_ADDR` に入れ、loopback の宛先を書き換えないため、コンテナの中の `127.0.0.1` はコンテナ自身を指す。届かないなら、個人の手元のサーバの形では、コンテナの中の `bao` が使えない
- 個人の 1 人の利用で、`version: 2`（グループ別の置き場）と `group_aliases` が要るか。要らないなら、個人の形の既定をどうするか。アカウントグループの宣言は必須で、`default` は予約語として弾かれる（#315）。backend を問わず各プロジェクトの `env` に `DEVBASE_ACCOUNT_GROUP` が要るため、個人の形で宣言するグループ名（例: `personal`）を合わせて決める
- AppRole のほかに、個人の形で token による認証を足す価値があるか（足すなら、token の保存先と期限切れの扱い）
- 雛形のポリシーで、今の受け入れ条件（他人のパスは 403、チーム共通への書き込みは権限のある人だけ）が満たされるか。実機の OpenBao（2.6 系）で確かめる

## 決めること

- **devbasex が共通の OpenBao サーバを 1 台運用する案は採らない（2026-09-26 に決定）。** 利用者が個人またはチームで自分のサーバを立てる形（セルフホスト）を前提にする。試用のための共通サーバも、この課題では作らない。理由は次の 4 つ
  - 全利用者の機密が 1 か所に集まり、侵害されたときの被害が全利用者に及ぶ。その責任を OSS の運営が負う
  - 利用者と端末の資格情報の発行・失効、濫用への対応、可用性、費用が続く。ツールの開発ではなくサービスの運営になる
  - 機密を自前で持ちたいから OpenBao を選ぶ利用者が多い。手順と雛形があれば、同じ構成を誰でも再現できる
  - 多数の他人で 1 台を共有すると、ポリシーの誤りがそのまま他人の機密の漏れになる
- ポリシーの雛形とサーバを試す構成をどこに置くか（`docs/` か、配布物に含めるか）
- 個人・チーム・既存のサーバの 3 つの形を、1 つの文書にまとめるか分けるか
- `devbase env backend use openbao` に、個人の形の初期設定を助ける機能（例: ポリシーの雛形を書き出す副命令）を足すか、文書だけにするか

## 完了条件

- 管理者のいない個人が、公開の文書と雛形だけで OpenBao サーバを立て、`devbase env backend use openbao` で接続し、`env set` / `env get` / `devbase up` の機密の読み込みまで通せる
- チームで 1 台立てたとき、本人以外の個人の置き場が 403 になり、チーム共通への書き込みが権限のある人だけに限られることを、雛形のポリシーで確かめてある
- 利用者向けの文書と確定仕様が、特定の組織のサーバや運用の決まりを前提にしていない

## 目的

- 組織の管理者がいない個人や小さなチームが、公開されている文書と雛形だけで自分の OpenBao サーバを立て、
  devbase の OpenBao backend で機密を扱えるようにする
- 利用者向けの文書と確定仕様から、特定の組織が運用するサーバと運用の決まりを前提にした記述を無くす

## 前提

- 前提 1: devbasex は共通の OpenBao サーバを運用せず、試用のための共通サーバも作らない（2026-09-26 の決定）
- 前提 2: 認証は今の AppRole（利用者ごとの `role_id`・端末ごとの `secret_id`）だけで、token による認証は足さない（2026-10-11 の決定）
- 前提 3: 個人の形も `version: 2`（`openbao.layout: group`）を使い、プロジェクトが宣言するアカウントグループは `personal` とする（2026-10-11 の決定）。個人の形で `group_aliases` は使わない
- 前提 4: 対象の OpenBao は base イメージの `bao` と同じ 2.6 系（`containers/base/Dockerfile` の `ARG BAO_VERSION=2.6.2`）とする。ほかの版での動作は確かめない
- 前提 5: devbase がサーバへ送る要求（4 経路のパス・KV v2 の API・AppRole のログイン）は変えない。サーバの側の雛形と文書を、今の devbase の要求に合わせる
- 前提 6: `bao server -dev` は機密を記憶にだけ置き、止めると消える。試用の構成は本物の機密を置く場所としては案内しない
- 前提 7: 実機の確認は、利用者の実際の環境の `devbase up`（P3）を使わず、作業用のプロジェクトと試用のサーバで行う。利用者の環境での確かめはリリース後テストで利用者が行う

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| セキュリティ | ポリシーの雛形は、受け入れ条件 12 に並べた権限のほかを許さない（本人以外の個人の置き場・`sys/` の管理の経路を利用者のポリシーに含めない）。文書の例に実の token・`secret_id`・root token の値を書かない。devbase の接続に root token を使う手順を示さない。`secret_id` をコマンド引数で渡す手順を示さない（今の `--secret-id-stdin` を使う） |
| 運用・保守性 | 雛形と試用の構成は OpenBao の版を 1 か所に書き、base イメージの `BAO_VERSION` と同じ 2.6 系に揃える |
| システム環境 | 試用の構成は macOS の Docker Desktop と Linux の Docker の両方で動く手順を示す。片方でしか確かめていなければ、文書に確かめた環境を書く |
