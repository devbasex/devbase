## 目的

- 固有の語が再び持ち込まれたら、マージの前に Pull Request の検査で気づける
- 同じ検査を、手元で push の前に打てる
- 検査が見張る語の一覧そのものは、公開のリポジトリ・CI のログのどちらにも出ない

## 前提

- 前提 1: 語の一覧は「1 行 1 語」の平文である。空行と `#` で始まる行は読み飛ばす。語は正規表現ではなく文字列として扱い、大文字小文字を区別せずに部分一致で探す（#294 の AC2 と同じ判定）
- 前提 2: 一覧には、一般の英単語と重なる語（#294 の表のアカウントグループの 1 語など）を入れない。そうした語は、その語を含むより長い固有の名前で見張る。一覧の中身は利用者が決め、この課題では決めない
- 前提 3: 手元では、一覧を追跡されない場所から読む。渡し方（環境変数・オプション・既定の置き場）と既定の置き場のパスは設計で決める。置き場はリポジトリの外か `.gitignore` 済みの場所に限る
- 前提 4: CI では、一覧を GitHub Actions の secret から読む。secret の名前は設計で決める。**secret の登録と更新は人が行う**（共通原則 C1）。この課題の Pull Request は secret を読むジョブを足すだけで、secret の値に触れない
- 前提 5: secret を読めない実行（フォークからの Pull Request・secret が未登録のリポジトリ）では、一覧が無い扱いにする。検査を飛ばして成功で終わり、飛ばしたことを出力に書く（#294 の前提 4）
- 前提 6: 検査の対象は `git ls-files` が返す追跡されたファイルである。中身を文字列として読めないファイル（バイナリ）は対象から外し、外したことは数だけを出す
- 前提 7: 例外は #294 の AC2 の 2 つ（`LICENSE` の著作権表示と `.ndf/mvv.json` の `approved_by`）だけである。例外の定義はパスと位置で書き、語を書かない。例外の定義を公開のファイルに置くかどうかと形は設計で決める
- 前提 8: AC9 の確認では、公開の git の履歴に既に出ている語（#294 は履歴を書き換えないため、新たな露出にならない）を 1 つ足した検証用のブランチで Draft の Pull Request を開き、検査の失敗を確かめたら Pull Request を閉じてブランチを消す。secret はそれより前に人が登録しておく
- 前提 9: この課題の Pull Request は、②〜④（#350・#351・#352）が `main` へ入った後にマージする。①（#349）も同じく先に入っている。検査のジョブが入った時点で `main` が 0 件でないと、以後のすべての Pull Request が落ちるため

## 対象範囲

含む:
- 語の一覧を読み、追跡されたファイルから語を探す検査のスクリプト（手元と CI で同じもの）
- CI（`.github/workflows/ci.yml`）へ、secret の一覧で検査を走らせるジョブを 1 つ足す
- 検査のスクリプトの単体テスト（語の一覧は `tmp` のファイルで渡す。テストの語は架空の語にする）
- 手元での打ち方の説明（開発者向けの文書）
- ②〜④が入った `main` で、検査が 0 件で通ることの確認（#294 の AC2）

含まない:
- 語の一覧の中身の決定と、secret への登録（人が行う）
- `main` の必須チェックへこのジョブを登録すること（リポジトリの保護設定の変更。未決へ回す）
- git の履歴・マージ済みの Pull Request と issue の本文の検査（#294 の対象外と同じ）
- 追跡されていないファイルの検査（`.gitignore` 済みのものは #349 が扱う）
- 置き換えそのもの（①〜④が行う）
- pre-commit などの git のフックへの組み込み

## ドメインイベント

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | 人が語の一覧を secret に登録した | 人の操作（C1） | 未登録なら E3 で一覧が無い扱いになる | — |
| E2 | 開発者が手元で語の一覧を置いた | 人の操作 | 置いていなければ E3 で一覧が無い扱いになる | — |
| E3 | 検査が語の一覧を読んだ | 手元での実行、または CI のジョブの開始 | 一覧が無い・空: 飛ばしたと出して 0 で終わる。一覧を読めない（権限・文字コード）: 理由を出して非 0 で終わる | CI では E1、手元では E2 |
| E4 | 検査が追跡されたファイルの一覧を得た | E3 の後 | `git` が使えない・リポジトリの外: 理由を出して非 0 で終わる | E3 |
| E5 | 検査が語を含む行を見つけた | E4 の後の走査 | — | E4 |
| E6 | 検査が結果を出して終わった | 走査の終わり | 当たりがあれば非 0、無ければ 0 | E5 |
| E7 | CI のジョブが Pull Request を失敗にした | E6 が非 0 | — | E6 |

## 用語

| 用語 | 意味 |
| --- | --- |
| 固有の語 | 作成者の所属組織・顧客・社内プロダクト・個人に固有の名前（#294 の「語ごとの出現」の表の語） |

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| セキュリティ | 語の一覧は secret と追跡されない置き場にだけ置き、ログ・成果物（artifact）・Pull Request のコメントに出さない。ジョブの権限は `contents: read` だけにする |
| 性能・拡張性 | 追跡されたファイル全件（現状 約 460 件）の走査が CI のジョブで 1 分以内に終わる |
| システム環境 | 手元は macOS と Linux のどちらでも打てる（Python 3.10 以上、`git` があること） |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| AC1〜AC6・AC8 | 検査のスクリプトの単体テスト（`tmp` に作った git のリポジトリと語の一覧で打つ） |
| AC7・AC11 | 手元の実際の一覧で検査を打つ。CI では `main` の Run の結果 |
| AC9・AC10 | 前提 8 の検証用の Pull Request の Run。フォーク相当は secret 未登録の状態の Run か、secret を渡さない起動の単体テスト |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | CI 用のスクリプトは `.github/scripts/`（`changelog_check.py` と同じ置き場）、そのテストは `tests/ci/`。置き場の最終決定は設計 |
| コーディング規約 | 既存の CI の検査（`ruff check --select=E9,F63,F7,F82 lib`・`python -m compileall`）と、`changelog_check.py` の書き方（モジュールの docstring に起動の仕方を書く） |
| テスト戦略 | スクリプトは単体テストで全分岐（当たり・0 件・一覧なし・空・例外・未追跡）を見る。ワークフローは定義を読むテストで見る。secret を使う実行は AC9 の 1 回の確認で見る |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | テストとテスト用の一覧に架空の語だけを使う。全体テストを走らせる |
| 確認してから行う | secret の登録・更新（人が行う。C1）。必須チェックへの登録。検証用の Pull Request で公開の履歴に無い語を使うこと |
| 行わない | 語の一覧を公開のファイル・ログ・Pull Request の本文とコメントへ書くこと。git の履歴の書き換え |
