# #463: VS Code Server（~/.vscode-server）をコンテナごとのボリュームに重ねて持ち、更新のたびに旧版が溜まる

正は課題の本文（#463）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

`devbase_vscode_{project}_{index}` はコンテナ 1 つに 1 本で、VS Code Server の本体（`bin/<commit>`）を各ボリュームが別々に持つ。VS Code の更新のたびに新しい版が入り、古い版が残るため、ボリュームが溜まっていく。

手元の端末で測った値（2026-10-12）:

| 項目 | 値 |
| --- | --- |
| `devbase_vscode_*` の合計 | 約 40GB（17 本） |
| うち `bin/` の旧版（各ボリュームの最も新しい 1 版を除いたもの） | 約 21GB。`bin/` に 8 版を持つボリュームが 3 本、7 版が 1 本 |
| `extensionsCache/` | 約 3.4GB |
| 同じ拡張の旧版の重複 | 例: `anthropic.claude-code` が 3 版、`openai.chatgpt` が 2 版（各 0.9GB） |

コンテナごとに分けているのは、VS Code Server が「1 マシン 1 セット」の状態（`data/Machine/.connection-token-<commit>` など）を持ち、同時に書くと接続トークンを奪い合うためとされている（`docs/user/container-operations.md` の「VS Code Server の永続化」）。この奪い合いを実機で確かめた記録は無い。版ごとに中身が変わらない `bin/<commit>` には、この理由はそもそも当たらない。

## 案

`~/.vscode-server` を丸ごと全コンテナ共通の 1 本のボリュームにする。共有して困る理由として挙げてきた「接続トークンの奪い合い」が実際に起きるかは確かめていない（下の 7〜10）。問題が出た部分だけをコンテナごとに戻す。戻す順は `data/` → `extensions/` で、`bin/` は最後まで共有する。

| 置き場 | 中身 | 共有 |
| --- | --- | --- |
| `bin/<commit>` | サーバーの本体。版ごとに不変 | 共有する（案） |
| `extensions/` | 拡張。`extensions.json` を各サーバーが書き換える | 共有する（案。4〜6 を確かめる） |
| `data/` | 接続トークン・マシンの設定・ログ・`User/` の状態（SQLite） | 共有する（案。7〜10 を確かめる） |

## 実機で確かめること

1. 2 つのコンテナで初めて同時に attach し、同じ版の `bin/<commit>` を同時にダウンロード・展開しても壊れないか（片方が展開途中の版を使わないか）
2. VS Code Server が使わなくなった古い版を `bin/` から消すとき、別のコンテナが使っている版まで消さないか
3. 既存の `devbase_vscode_*` からの移り方（既存の `bin/`・`extensions/` を共通のボリュームへ寄せるか、捨てて取り直すか）
4. 2 つのコンテナで拡張のインストール・更新・アンインストールが同時に起きたとき、`extensions/extensions.json` が壊れたり片方の書き込みが失われたりしないか
5. 拡張の自動更新が旧版に `.obsolete` の印を付けて消すとき、別のコンテナがまだ読み込んでいる旧版まで消さないか
6. サーバーの版が違うコンテナ同士（片方だけ VS Code を更新した状態）で同じ `extensions/` を使えるか（拡張は対応するエンジンの版で入る版が変わる）
7. 接続トークン `data/Machine/.connection-token-<commit>`: 既にあれば読み、無ければ作る作りか。2 つのコンテナで初めて同時に起動したとき、両方が書いて後勝ちになり、先に起動した側の接続が切れるか（今の文書の「奪い合う」が実際に起きるか）
8. `data/User/globalStorage`・`data/User/workspaceStorage` の `state.vscdb`（SQLite）を複数のサーバーが同時に開いたとき、ロックの待ちや書き込みの失敗が出ないか
9. `data/logs/` が起動ごとに別のディレクトリになり、ぶつからないか
10. `data/Machine/settings.json` をコンテナ間で同じにして困る設定が devbase の使い方にあるか

## どこで見つけたか

スプリント m8a（#368 の受け入れ条件 9 の確認）で、ホストのディスクが満杯になった後に空きを作る作業で `docker system df -v` を見たとき。このときは各ボリュームの `bin/` の旧版・`extensionsCache/`・`extensions.json` に無い拡張の旧版を手で消し、約 40GB から約 12GB にした。

## なぜこの変更の範囲外なのか

スプリント m8a の課題（#455 #368）はスナップショットの除外と補完のテストで、VS Code Server のボリュームの構成を含まない。`devbase_vscode_*` はスナップショットの対象外でもある。

## 確かめた範囲で減る量の見込み

今回の手元では、`bin/` の旧版が約 21GB、拡張の旧版の重複と `extensionsCache/` で数 GB。丸ごと共有すると、同じ版をプロジェクトとインスタンスの数だけ重ねて持つことが無くなり、合計は 1 本分（今回の最大のボリュームで約 2GB）に近づく。拡張を一度入れれば全コンテナで使える。

## 直さないと何が起きるか

VS Code の更新のたびに、各ボリュームへ 1 版（約 0.6GB）ずつ溜まり続ける。プロジェクトとインスタンスの数だけ同じ版を重ねて持つため、ホストのディスクを圧迫する。手で消さない限り減らない。

## 目的

- VS Code Server の本体と拡張を、プロジェクトとインスタンスの数だけ重ねて持たず、全コンテナで 1 組にする
- VS Code の更新のたびに本体の旧版が溜まり続けることを止め、手で消さなくてもホストのディスクを使う量に上限がある状態にする
- 窓のタイトル・接続の再開など、コンテナごとに分かれていることに頼る今の振る舞いを保つ

## 前提

- 前提 1（共有の範囲）: `~/.vscode-server` のうち `bin/`・`extensions/`・`extensionsCache/` とその他の直下の置き場を、共通の VS Code Server ボリューム 1 本に置く。`data/` はコンテナごとの VS Code Server の状態として、dev コンテナ 1 つに 1 本のボリュームを付ける。理由は、`data/Machine` に共有すると壊れるものが 2 つ見つかったためである（`.devport-<commit>` は後から書いた側の値になる。`window.title` は devbase がコンテナごとに違う値を書く。「実機で確かめることの扱い」の 7・10）。利用者の見立て「data も事実上問題ない」と違えるため、承認ゲート 1 で利用者が確かめる
- 前提 2（共有の単位）: 共通の VS Code Server ボリュームは端末に 1 本で、アカウントグループで分けない。置くのはサーバーの本体と拡張のコードで、認証の情報を持たない。認証の情報や拡張の保存する状態は `data/` に入り、コンテナごとに分かれたままになる
- 前提 3（移り方）: 旧形式の VS Code Server ボリュームの中身は、新しいボリュームへ写さない。本体は最初の attach で取り直し（約 215MB、約 55 秒）、利用者が手で入れた拡張は入れ直す。`data/` も引き継がない（今の文書も「失っても attach し直せば再取得されます」としている。`window.title` は `devbase up` が書き直す）。写すと、ボリュームの丸写しでホストのディスクが埋まる落とし穴（AGENTS.md）に当たる
- 前提 4（後片付け）: devbase は旧形式の VS Code Server ボリュームを消さない（C4）。`devbase up` が見つけたときに名前と消し方を案内し、消すのは利用者が行う
- 前提 5（本体の旧版の片付け）: Dev Containers 拡張（0.469.0 で確かめた）は、devbase の attach の形では `bin/` の旧版を消さない（「実機で確かめることの扱い」の 2）。devbase のコンテナの起動で、`bin/` の版を新しい順に一定の数だけ残して古い版を消す。残す数は設計で決め、3 版以上とする
- 前提 6（片付けの置き場）: 本体の旧版の片付けと、権限の用意は、コンテナの entrypoint（`devbase_setup_vscode_server_dir`）に置く。entrypoint の変更は base を建て直すまで効かない（AGENTS.md の落とし穴）。この課題で base の道具とその版は変えない（P1 に当たらない）
- 前提 7（拡張の集まり）: 拡張は全コンテナで同じ集まりになる。あるプロジェクトのためだけに入れた拡張も、ほかのプロジェクトのコンテナの拡張ホストに読み込まれる。拡張はプロジェクトの設定・機密・データを持たないため、プロジェクトの境界（Value 3）には当たらないとみなす

## 対象範囲

含む:
- 共通の VS Code Server ボリュームと、コンテナごとの VS Code Server の状態のボリュームを作る・dev インスタンスへ付ける（`lib/devbase/volume/manager.py`・`lib/devbase/volume/compose.py`）
- コンテナの起動で `~/.vscode-server` と `~/.vscode-server/data` を開発ユーザーが書ける形にし、`bin/` の旧版と同時の展開の残りを片付ける（`containers/base/entrypoint.sh` の `devbase_setup_vscode_server_dir`）
- `devbase up` が旧形式の VS Code Server ボリュームを見つけたときの案内
- 文書（`docs/user/container-operations.md` の「VS Code Server の永続化」とボリュームの表）、`CHANGELOG.md` の `[Unreleased]`
- 上の振る舞いのテスト（`tests/volume/`・`tests/containers/`）

含まない:
- 旧形式の VS Code Server ボリュームを devbase が消す・写す・付けること
- 拡張の版の選び方・自動更新の振る舞いを変えること（VS Code と Dev Containers 拡張の持ち物）
- `extensionsCache/` と `extensions/` の旧版の片付け（`extensions/` の `.obsolete` の版は VS Code Server が起動時に消す。「実機で確かめることの扱い」の 5）
- スナップショットの対象を変えること
- Cursor など `~/.vscode-server` 以外のサーバーの置き場（`~/.cursor-server` など）
- base イメージに入れる道具とその版の変更（P1）

| E4 | entrypoint が `bin/` の旧版と、同時の展開の入れ子の残りを片付けた | コンテナの起動 | 消せなくても起動を止めず、WARNING を出す | E3 |
| E5 | VS Code の attach が本体を `bin/<commit>` に置いた（無いときだけ） | 利用者の attach | 同時の展開で片方が失敗すれば、その窓の接続が失敗し、やり直しで繋がる（「実機で確かめることの扱い」の 1） | E3 |
| E6 | VS Code Server が接続トークンと `.devport` を `data/Machine` に書いた | E5 の後のサーバーの起動 | — | E5 |
| E7 | `devbase up` が `window.title` を `data/Machine/settings.json` に書いた | `devbase up` の起動の後の処理 | 今と同じ（警告して続ける） | E3 |
| E8 | 拡張を入れた・更新した・消した | 利用者の操作・自動更新 | — | E5 |
| E9 | 別のコンテナのサーバーの起動が、`.obsolete` の付いた拡張の版を消した | ほかのコンテナの E6 | 動いている窓の拡張が使えなくなり得る（手動確認 M3） | E8 |
| E10 | `devbase up` が旧形式の VS Code Server ボリュームを見つけ、名前と消し方を案内した | `devbase up` | ボリュームの一覧が取れなければ案内を出さずに続ける | E1 |
| E11 | 利用者が旧形式の VS Code Server ボリュームを消した | 利用者の操作 | 使っているコンテナが残っていれば `docker volume rm` が断る | E10 |

## 用語

| 用語 | 意味 |
| --- | --- |
| 共通の VS Code Server ボリューム | すべての dev コンテナが `~/.vscode-server` に付ける 1 本のボリューム。`bin/`・`extensions/`・`extensionsCache/` を持ち、`data/` を持たない |
| コンテナごとの VS Code Server の状態 | `~/.vscode-server/data`。dev コンテナ 1 つに 1 本のボリュームを付ける |
| 旧形式の VS Code Server ボリューム | この課題より前の `devbase_vscode_<project>_<index>`。`~/.vscode-server` を丸ごと持つ |

## 受け入れ条件

ボリュームと compose:

- [ ] 1. `devbase up` / `devbase scale` は、共通の VS Code Server ボリュームが無ければ 1 本作り、あれば作らない。プロジェクト・インスタンス・アカウントグループが違っても同じ 1 本である
- [ ] 2. 生成した compose の dev インスタンスは、どれも共通の VS Code Server ボリュームを `/home/ubuntu/.vscode-server` に付け、インスタンスごとに違うボリュームを `/home/ubuntu/.vscode-server/data` に付ける
- [ ] 3. コンテナごとの VS Code Server の状態のボリュームの名前は、プロジェクトとインスタンス番号で決まり、どのプロジェクト名でも、旧形式の VS Code Server ボリュームの名前（`devbase_vscode_<project>_<index>`）とも共通の VS Code Server ボリュームの名前とも重ならない
- [ ] 4. 前提: コンテナ A とコンテナ B（別のプロジェクト）が共通の VS Code Server ボリュームを付けている。操作: A の `code-server` で拡張を入れる。結果: B の `code-server --list-extensions` にその拡張が出る
- [ ] 5. プロジェクトの compose が `/home/ubuntu/.vscode-server` を自分で付けているとき、devbase は `~/.vscode-server` にも `~/.vscode-server/data` にもボリュームを足さない（今と同じ）
- [ ] 6. 生成した compose に、旧形式の VS Code Server ボリュームが現れない

コンテナの起動:

- [ ] 7. 前提: 共通の VS Code Server ボリュームの `bin/` に、残す数より多い版がある。操作: コンテナを起動する。結果: 新しい順に残す数の版だけが残り、それより古い版のディレクトリが無い
- [ ] 8. 前提: `bin/<commit>/` の中に、同時の展開で残った入れ子の本体（`vscode-server-linux-*` など、`product.json` を持つディレクトリ）がある。操作: コンテナを起動する。結果: 入れ子の本体が無く、`bin/<commit>/bin/code-server` は残っている
- [ ] 9. 片付けで消せないもの（権限が無い・ほかのコンテナが先に消した）があっても、コンテナの起動は止まらず、消せなかったパスを WARNING の行に出す（ほかのコンテナが先に消したときは出さない）
- [ ] 10. 空のボリュームを付けて起動すると、`~/.vscode-server` と `~/.vscode-server/data` は開発ユーザーが書ける。この課題より前の entrypoint を持つイメージ（建て直す前の base と、その上の派生イメージ）でも、`~/.vscode-server/data` は開発ユーザーが書ける

移り方と後片付け:

- [ ] 11. 前提: 旧形式の VS Code Server ボリュームが 1 本以上ある。操作: `devbase up`。結果: 旧形式のボリュームの名前と、消すコマンドが案内に出る。devbase はそのボリュームを消さず、付けず、中身を読まない
- [ ] 12. 前提: 旧形式の VS Code Server ボリュームが無い。操作: `devbase up`。結果: 案内は出ない
- [ ] 13. スナップショットの対象は変わらない（共通の VS Code Server ボリュームとコンテナごとの VS Code Server の状態のボリュームは、どちらも対象外）

文書:

- [ ] 14. `docs/user/container-operations.md` の「VS Code Server の永続化」とボリュームの表が、共有する置き場とコンテナごとの置き場、共有する理由、`data/` を分ける理由（`.devport` と `window.title`）、移ったあとの最初の attach で本体を取り直すこと・手で入れた拡張を入れ直すこと、旧形式のボリュームの消し方、`bin/` に残す版の数を書いている。「接続トークンを奪い合う」という記述が無い
- [ ] 15. `CHANGELOG.md` の `[Unreleased]` に、ボリュームの構成が変わること、最初の attach で取り直すこと、旧形式のボリュームを利用者が消すことを書いている

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 共通の VS Code Server ボリュームの `bin/` に残る版の数は、コンテナの数・プロジェクトの数・VS Code の更新の回数に依らず、残す数（前提 5）を超えない。コンテナの起動の後に、入れ子の本体が残らない |
| 移行性 | 移る対象は無い（写さない）。切り戻し: devbase をこの課題より前の版へ戻すと、消していない旧形式の VS Code Server ボリュームを前と同じように付ける。共通の VS Code Server ボリュームとコンテナごとの VS Code Server の状態のボリュームは残るだけで害が無い |
| セキュリティ | 共通の VS Code Server ボリュームに、接続トークン・拡張の保存する状態・マシンの設定が入らない（それらは `data/` にあり、コンテナごとに分かれる） |
| システム環境 | macOS の Docker Desktop と Linux の Docker で同じ振る舞いになる。新しい Compose のオプションを使うなら、要る Compose の版と、それより前の版での扱いを設計で決める（AGENTS.md の落とし穴） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | CLI の引数と出力は変わらない（`devbase up` の案内の行が増える）。生成する compose のボリュームの構成が変わる。旧形式の VS Code Server ボリュームを使い続ける経路は持たない（`互換なし`。ただし中身は VS Code が取り直せるもので、切り戻しで元へ戻る） |
| データ | 旧形式の VS Code Server ボリュームは使わなくなり、残る。移行はしない（前提 3） |
| 既存の振る舞い | 移った後の最初の attach で本体（約 215MB）を取り直す。コンテナに手で入れた拡張は入れ直しが要る。`data/Machine/settings.json` の利用者の設定（`window.title` 以外）は引き継がれない |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `env -u DEVBASE_ROOT uv run --locked pytest tests/ -q`（compose の生成は `tests/volume/test_compose_vscode.py`、ボリュームの用意は `tests/volume/test_manager_vscode.py`、entrypoint の関数は `tests/containers/test_entrypoint_vscode_server.py` の形） |
| 静的解析 | `uvx ruff check --select=E9,F63,F7,F82 lib`、`python3 .github/scripts/proper_term_check.py`、`devbase-base:latest` の shellcheck で `containers/base/entrypoint.sh` |
| 実機（担当が打てる範囲） | 受け入れ条件 4・7〜10 は、空の作業用ボリュームと手元の `devbase-base:latest` の `docker run --rm` で確かめる。受け入れ条件 10 の「この課題より前の entrypoint」は、建て直していない今の `devbase-base:latest` がそれに当たる。新しい entrypoint はイメージを建てずに、関数をボリュームを付けたコンテナの中で走らせて確かめる。`devbase up` は打たない |
| 手動確認（マージ前） | M1〜M3。新しい devbase で `devbase up` が要るため、conductor が P3 の承認を取ってから打つか、利用者が行う。担当は打たない |
| 手動確認 | M4・M5。リリース後テストで確かめる |

手動確認の項目:

- M1（マージ前）: 別のプロジェクトの 2 つのコンテナへ VS Code を attach する。両方の窓が使え、窓のタイトルがそれぞれのコンテナ名で始まる。片方の窓で「ウィンドウの再読み込み」をしても、その窓が同じコンテナへ繋がり直す
- M2（マージ前）: M1 の状態で、片方の窓から拡張を入れ、もう片方の窓を再読み込みすると、その拡張が使える。両方の窓で同じ拡張の更新を同時に行っても、どちらの窓の拡張も使える
- M3（マージ前）: 片方の窓で拡張を更新した（旧版に `.obsolete` が付いた）あと、3 つ目のコンテナへ attach する。残っている窓でその拡張が使えなくなったら、その窓の再読み込みで使えるようになるかを記録する。再読み込みで直らないときは、`extensions/` もコンテナごとに戻す（S2 の規則）かを利用者が決める
- M4（リリース後）: 片方の端末の VS Code だけを更新し、版の違う 2 つのサーバーが同じ共通の VS Code Server ボリュームを使う。どちらの窓でも拡張が使える
- M5（リリース後）: VS Code の更新の後、複数の窓を一度に開き直す。その後にコンテナを起動し直すと、`bin/<新しい commit>/` に入れ子の本体が残っていない

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | AGENTS.md の「このリポジトリ」。`projects/*` はプラグインのリポジトリで、触らない |
| コーディング規約 | 周りのコードに合わせる。`lib/` は ruff の CI の規則、`entrypoint.sh` は ShellCheck |
| テスト戦略 | compose の生成とボリュームの用意は単体のテストで、entrypoint の片付けは関数を一時のディレクトリで走らせるテストで担保する。VS Code の振る舞い（拡張の同時の操作・`.obsolete`）は担当の実機の確かめと手動確認で担保する |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 全体のテスト・lint・固有の語の検査を push の前に打つ。実機の記録は中立の名前（`proj-a` など）で書く。作業用のボリュームは記録を書いたら消す |
| 確認してから行う | 前提 1（`data/` をコンテナごとに戻す）と前提 3（写さずに取り直す）は承認ゲート 1 で利用者が確かめる。生成する compose のボリュームの構成の変更は承認ゲート 2 で人が見る |
| 行わない | 旧形式の VS Code Server ボリュームを消す・写す・付ける。担当が `devbase up` を打つ（作業用のプロジェクトも含む）。base イメージを建て直す。base の道具とその版を変える |

## 未決

| 項目 | 誰が決めるか | 期限 |
| --- | --- | --- |
| `bin/` に残す版の数（3 版以上） | 設計 | 承認ゲート 1 |
| 2 つのボリュームの名前と、`data/` を付ける形（入れ子のマウントか、別の置き場への symlink か） | 設計 | 承認ゲート 1 |
| 旧形式の VS Code Server ボリュームの案内を `devbase up` のたびに出すか、出す回数を絞るか | 設計 | 承認ゲート 1 |
| M3 で拡張が使えなくなり、再読み込みで直らないときに `extensions/` もコンテナごとに戻すか | 利用者 | M3 の後 |

## MVV との突き合わせ

反する疑いは無い。根拠: Value 1（本体と拡張を取り直すのは移った後の最初の 1 回だけ）、Value 2（`data/` はコンテナごとのボリュームに残り、作り直しで失わない）、Value 3（プロジェクトごとの状態は `data/` に分かれたまま。共有する拡張はプロジェクトの設定・機密・データではない。前提 7）、C4（旧形式のボリュームを devbase が消さない）、P1（base の道具とその版を変えない）、P3（マージ前の手動確認の `devbase up` は承認を取ってから打つ）。
